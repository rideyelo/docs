This page collects every known failure path across ride payments, tips, payouts, QR payments, and Connect accounts. Use it when a rider disputes a charge, a driver reports missing money, or an alert fires. The mechanics behind each row are on the linked pages.

## Failure matrix

### Ride authorization and capture

Ride money moves through ride operations. A command reserves a `RideOperations` row, then executes Stripe steps from it. Most failures below leave that row `pending` (the `ride_operation` job keeps retrying) or `quarantined` (nothing retries). Either state blocks every other command on the ride. See [Ride operation journal](/engineering/payments/ride-operation-journal).

| Failure | Detection | Rider sees | Driver sees | Money state |
| --- | --- | --- | --- | --- |
| Accept rejected at reservation | No operation row | Nothing. Ride stays searching | "Ride Unavailable" | No hold |
| Missing consent, payment method, customer, or connected account at accept | No operation row. Server error from `ValidateRidePaymentPreparation` | Nothing | Accept fails | No hold |
| Card declined at accept or promotion | Operation `failed`. Ride `complete` with `cancel_reason = 'Payment Failed'` | `ride_payment_failed` push | "Payment Failed". Next queued ride is promoted | Intent canceled. No hold |
| Stripe or network error on clone, create, or confirm | Operation `pending` with an open step | `transition_pending` on the snapshot | Accept returns a server error. Ride is assigned | No hold, or an unconfirmed intent. The retry reuses the same idempotency key |
| Provider object contradicts the frozen request | Operation `quarantined`, outcome `authorization_requires_reconciliation` or `clone_requires_reconciliation` | `transition_pending` | Other commands on the ride return "Ride Unavailable" | Unknown. Needs a person |
| Capture fails at `complete` with a Stripe or network error | Operation `pending` | Nothing | Complete returns a server error. Ride stays `in_progress` | Hold intact |
| DB write fails after a verified capture | Operation `pending` with a resolved `capture` step | Charged | Ride looks in progress until the job finalizes | Captured. The next attempt finalizes without calling Stripe |
| Capture finds the intent canceled, expired, or captured for another amount | Operation `quarantined`, outcome `capture_requires_reconciliation` | `transition_pending` | Ride stuck in its current status | Whatever Stripe shows |
| Job attempts exhausted on a `pending` operation | Recovery quarantines with `job_exhausted`. Warn log `ride operation delivery recovery` | `transition_pending` | Ride stuck | Depends on the open step |
| Sweeper can't settle | `ride stuck past tip window for >1 hour, needs manual review`, every 5 minutes | Hold stays | Payout missing | Hold until Stripe expires it |

See [Ride PaymentIntent lifecycle](/engineering/payments/ride-payment-intents).

### Cancellation

| Failure | Detection | Result |
| --- | --- | --- |
| No current quote on a ride with a hold | "Review cancellation fee" | Cancel rejected. The rider reopens cancellation to get a fresh quote |
| Quote expired or the ride changed since the quote | "Ride Unavailable" | Cancel rejected. No operation |
| Fee capture or void fails with a Stripe or network error | Operation `pending` | Cancel returns a server error. The ride keeps its status and accepts no other command while the job retries |
| Void finds the intent already captured | Operation `quarantined`, outcome `void_requires_reconciliation` | Ride stuck in its current status |
| Unmatched request expires with a hold still attached | System `cancel` operation with a `void` step | The hold is voided before the ride completes. If the void can't be verified, the ride stays `confirmed` with an unresolved operation |

### Tips

| Failure | Detection | Result |
| --- | --- | --- |
| Tip needs authentication | Rate returns `tip_status: requires_action` | Mobile ignores it. The server abandons and cancels the intent 30 minutes after the first `requires_action` observation |
| Tip intent declined | `tip` operation `failed` | Rate returns `tip_status: none`. Rating saved. No charge |
| Tip still processing at Stripe | "Tip pending" | Rating fails. The job keeps polling |
| Driver or fleet has no connected account, or the rider has no saved method | Server error at reservation | Rating fails. The mobile screen shows "Could not confirm your review" |
| Tip on a free ride that is still `pending_rider_rating` | Server error at reservation ("invalid dedicated tip fare settlement") | Rating fails. See [Free rides](/engineering/payments/ride-tips#free-rides) |
| Tip under $0.50 as a dedicated charge | Stripe `amount_too_small` on `create_tip` | Rating fails. The `tip` operation stays `pending` until its job is exhausted, then quarantines |
| Different tip amount while one is unfinished | "Ride Unavailable" | Rating fails |

See [Ride tip charging](/engineering/payments/ride-tips).

### Webhooks

| Failure | Detection | Result |
| --- | --- | --- |
| Signature, timestamp, or API version mismatch | `[stripe-webhook] signature verification failed` | 500. Nothing applied. Stripe retries |
| Secret missing | `[stripe-webhook] STRIPE_WEBHOOK_SECRET is empty` | Same |
| Payout or account event for a fleet or unknown account | `failed to handle payout event`, `failed to handle account updated` | 500 on every retry |
| DB error while waking ride operations on a `payment_intent.*` event | `failed to wake ride payment operation` | 500. The `payment_intent.succeeded` payout write doesn't run for that delivery. Stripe retries |
| `payment_intent.canceled`, `processing`, `requires_action`, or `amount_capturable_updated` | `[stripe-webhook] payment intent update` | 200. Only the wake-up runs. No ride column changes |

See [Stripe webhooks](/engineering/payments/webhooks).

### Connect and payouts

| Failure | Detection | Result |
| --- | --- | --- |
| Missed `account.updated` | Reconciliation `overdue` count | Status corrected on the next daily reconcile |
| Stripe 429, 401, or 403 during reconcile | `Stripe reconciliation integration deferred` | Global cooldown. All reconcile jobs snooze |
| Account deleted in Stripe | Reconcile category `stripe_account_invalid` | Rechecked weekly. Any rides still pointing at it can't settle |
| Instant payout ineligible | Stripe error on `POST /earnings/payouts/instant` | Driver sees Stripe's error body |
| Breaker open | `CIRCUIT_BREAKER_TRIPPING` with component `stripe`, Slack alert | 60 seconds of failures for every wrapped call. See [Stripe object map](/engineering/payments/stripe-object-map#resilience-per-call) |

See [Connect accounts and onboarding](/engineering/payments/connect-accounts) and [Payouts and earnings internals](/engineering/payments/payouts-and-earnings).

## Data invariants

These should hold. Each lists what enforces it and how the code can break it.

### Holds and rides

1. **A paid ride whose `accept` or `promotion` operation `succeeded` has a `payment_intent_id` and `stripe_merchant_id`.** Enforced by `attachPromotionPayment`, which writes them in the transaction that finishes the operation. The ride is already `driver_en_route` while that operation is `pending`, so the columns can be null on an assigned ride until it resolves.
2. **`Rides.stripe_merchant_id` owns `Rides.payment_intent_id`.** Both are written together by `AddRidePaymentIntent` from one verified receipt.
3. **The PaymentIntent's `metadata.driver_id` equals `Rides.driver_id` while assigned.** `verifyAuthorizationIdentity` checks it on every read. Intents created before the journal carry no `operation_id` metadata.
4. **At most one live hold per ride.** A requeue voids the hold before the ride rejoins matching, and expiry voids any hold before completing the ride. Both verify the void before changing the ride. A stray hold needs a quarantined operation or a manual change in Stripe.
5. **`pre_auth_amount` equals the Stripe `amount` divided by 100.** Both come from the same frozen `authorization_cents`.
6. **A ride has at most one `pending` or `quarantined` operation.** Enforced by the unique partial index `ride_operations_one_unresolved` and by `HasConflictingRideOperation`.

### Settlement

7. **A `complete` paid ride without cancellation has a captured PaymentIntent.** `freezeCompletionPayment` refuses to complete a paid ride with no recorded PaymentIntent, and every settlement finalizer verifies a capture receipt first.
8. **`driver_payout` equals what the connected account received for the fare, plus any tip.** Written by the finalizers from frozen cents. The `payment_intent.succeeded` webhook skips rides that have an operation row, so it can't overwrite them.
9. **`tip_amount` is nonzero only if a tip was collected.** The tip and its verified receipt commit in one transaction.
10. **Every paid, tips-enabled ride in `pending_rider_rating` leaves it within 24 hours plus one sweeper tick.** Broken for rides whose settlement is `pending` on a failing capture or `quarantined`. Free rides and tips-off rides have no window, and leave on the rider's rating.
11. **Canceled rides with a fee have `driver_payout` equal to the fee.** `CancelReservedRide` writes it with the cancellation.
12. **A `succeeded` or `failed` operation eventually has a row in `RideOperationEffectReceipts`.** The worker writes it after the ride board and queue summary reconcile, and recovery re-enqueues any terminal operation that lacks one.

### Accounts and QR

13. **Each `stripe_merchant_id` belongs to exactly one user, or to one or more fleets that are clones.** Not enforced by a unique constraint. `AccountUpdated` takes the fleet path whenever any fleet matches.
14. **`Fleets.stripe_status = complete` implies the account can take charges.** Only `payouts_enabled` and requirement lists are checked, not `charges_enabled`.
15. **Each Checkout Session produces at most one `QrPayments` row.** Enforced by the unique `stripe_session_id`.
16. **`QrPayments.fleet_id` is the fleet that received the money.** Broken for owner-operator driver links, which tag the driver's fleet while paying the driver's own account.

## Investigating a ride

<Steps>
  <Step title="Read the ride row">
    Check `status`, `cancel_phase`, `payment_intent_id`, `stripe_merchant_id`, `pre_auth_amount`, `tip_amount`, `tip_payment_intent_id`, `driver_payout`, `tips_enabled`, and `tip_window_expires_at`.
  </Step>
  <Step title="Read the ride's operations">
    List `RideOperations` for the ride, oldest first, with `kind`, `state`, `actor_type`, `outcome`, and `finished_at`. A `pending` or `quarantined` row is what's holding the ride. For that row, list `RideOperationSteps`: a step with a null `result` is the provider call that didn't resolve, and its `request` holds the exact PaymentIntent, account, and amount.

    ```sql
    SELECT o.id, o.kind, o.state, o.actor_type, o.outcome, o.created_at, o.finished_at,
           e.completed_at AS effects_completed_at
    FROM "RideOperations" o
    LEFT JOIN "RideOperationEffectReceipts" e ON e.operation_id = o.id
    WHERE o.ride_id = '<ride-id>'
    ORDER BY o.created_at;
    ```
  </Step>
  <Step title="Read the ride events">
    Filter for `ride_accepted`, `ride_auto_queued`, `queue_promoted`, `ride_completed`, `ride_canceled`, `auto_requeued`, `no_drivers_available`, `tip_captured`, and `tip_window_expired`. Each one written by an operation carries `operation_id` in its metadata. Rides from before the journal also have `merchant_selected`, `payment_intent_created`, `payment_processing_failed`, `payment_confirmed`, and `payment_canceled`. The dashboard ride timeline shows them. See [Rides](/dashboard/rides).
  </Step>
  <Step title="Read Stripe">
    Open the PaymentIntent on the connected account in `stripe_merchant_id`. Compare `amount`, `amount_capturable`, `amount_received`, `status`, and `metadata`. When the ride row has no intent yet, take the ID from the `create_authorization` or `create_tip` step result. A dedicated tip that hasn't succeeded exists only there.
  </Step>
  <Step title="Look for orphans">
    Search the connected account's PaymentIntents for `metadata.ride_id` equal to the ride. More than one uncaptured intent means a stray hold. Match each one to an operation through `metadata.operation_id` before canceling anything from the Stripe Dashboard.
  </Step>
</Steps>

## Signals worth alerting on

These log messages and metrics indicate money is stuck or out of sync. Search for them in Cloud Logging, or wire them to alerts. See [Observability](/engineering/observability).

| Signal | Source | Meaning |
| --- | --- | --- |
| `ride operation delivery recovery` at warn level, `quarantined` above 0 | `rideOperationRecoveryWorker` | A `pending` operation's job was discarded or cancelled. The operation is now `quarantined` and holds its ride |
| `ride operation delivery recovery` at info level, `requeued` above 0 | `rideOperationRecoveryWorker` | A missing `ride_operation` job was restored. Repeated counts for the same operation mean its effects keep failing |
| `ride stuck past tip window for >1 hour, needs manual review` | `AutoCaptureTipWindowExpired` | A settlement keeps failing. Check the ride's `settle_tip` operation |
| `Assigned ride awaits durable preparation` | `AutoAssignRide` | An automatic assignment committed but its authorization or route didn't finish in the request. The job owns the retry |
| A `ride_operation` job in `cancelled` | `rideOperationJobResult` | The operation is `quarantined` |
| `[stripe-webhook] signature verification failed` | `HandleStripeEvent` | Secret or API version mismatch. All webhooks are failing |
| `CIRCUIT_BREAKER_TRIPPING` with component `stripe` | `circuitbreaker.NewSettings` | Wrapped Stripe calls are failing fast for 60 seconds |
| `Stripe reconciliation coverage` at warning level | `reconciliationDispatchWorker` | Accounts are failed or overdue by more than 25 hours. Accounts Stripe rejects as invalid are counted separately and don't trigger it |

There's no admin endpoint to recapture, cancel, refund, or resolve a quarantined operation. All manual fixes happen in the Stripe Dashboard, and the Yelo rows must be corrected separately, because refunds and cancellations made in Stripe don't change the ride. `charge.refunded` isn't handled. `payment_intent.canceled` is routed to `PaymentService.PaymentIntentUpdated`, which only reschedules pending ride operation jobs and writes no ride column. See [Waking ride operations](/engineering/payments/webhooks#waking-ride-operations).

## Gotchas and edge cases

- **The decision is written before Stripe is called.** Each command commits its frozen amounts and account first, each step commits its request before the call and its receipt after, and the ride changes only in the transaction that finishes the operation. A crash between any two of those is resumed by the `ride_operation` job.
- **Quarantine has no tooling.** Nothing in the API resolves a quarantined operation. It holds its ride until someone writes the missing step result and finishes the operation by hand. See [Quarantine](/engineering/payments/ride-operation-journal#quarantine).
- **Unresolved means blocked.** A `pending` or `quarantined` operation rejects every other ride command, admin silent cancel, and expiry for that ride.
- **In-process sweepers.** `TipCapture` and the expiry sweep run in every API instance with no leader election. Correctness relies on deterministic command IDs, so every instance addresses the same operation.
- **No refunds in code.** Nothing in the API issues a refund, so a rider refund is always a manual Stripe action followed by a manual DB fix.
