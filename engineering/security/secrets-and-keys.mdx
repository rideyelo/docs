This page lists secrets by name only. It never includes values. For every variable, including non-secret settings, see [Environment variables](/reference/environment-variables). For how releases attach secrets, see [Deployment](/engineering/deployment).

## How secrets reach each runtime

| Runtime | Delivery | Where the binding is defined |
| --- | --- | --- |
| Production API (`yelo-api-testflight`, project `prod-yelo`) | Google Secret Manager, attached with `gcloud run deploy --update-secrets="$RUNTIME_SECRET_REFS"` | `_RUNTIME_SECRET_REFS` on the `yelo-api-release-manual` Cloud Build trigger. The list is trigger configuration, not in the repository |
| Production migration job | Secret Manager `yelo-api-migration-dsn` as `MIGRATION_DSN` | `cloudbuild.yaml` |
| Release Slack notice | Secret Manager `yelo-api-deploy-slack-webhook` as `SLACK_WEBHOOK_URL` | `cloudbuild.yaml` `availableSecrets` |
| E2E API (`yelo-api-e2e`) | Secret Manager, listed explicitly with `--set-secrets` | `cloudbuild.e2e.yaml` |
| Web sites | None. Only public `VITE_*` values from GitHub Actions variables, inlined at build time | `yelo-web/.github/workflows/firebase.yml` |
| Cloudflare workers | `wrangler secret put` | `yelo-web/workers/*/README.md` |
| Mobile app | Only public `EXPO_PUBLIC_*` values and EAS file variables | `yelo-frontend/eas.json`, `app.config.ts` |
| GitHub Actions | Repository and environment secrets | `.github/workflows/*.yml` in each repo |

GitHub Actions reach Google Cloud through Workload Identity Federation (`GCP_WORKLOAD_IDENTITY_PROVIDER`, `GCP_RELEASE_SERVICE_ACCOUNT` in `yelo-api`, and a fixed provider and service account in `yelo-web`). No long-lived Google service account key is stored in GitHub.

## yelo-api runtime secrets

"Rotation" describes what the code supports. Where the code has no overlap mechanism, rotation is a hard cut that invalidates whatever the old value protected.

### E2E secret set

`cloudbuild.e2e.yaml` attaches these Secret Manager entries to `yelo-api-e2e`: `yelo-e2e-dsn`, `yelo-e2e-jwt-key`, `yelo-e2e-redis-url`, `yelo-e2e-control-api-key`, `yelo-e2e-stripe-api-key`, `yelo-e2e-stripe-publishable-key`, `yelo-e2e-google-maps-api-key`, `yelo-e2e-mapbox-api-key`, `yelo-e2e-auth-state-key`, `yelo-e2e-auth-subject-key`, `yelo-e2e-auth-rate-key`, `yelo-e2e-auth-onboarding-key`, and `yelo-e2e-auth-refresh-key`. `Config.validateE2E` refuses to start if Twilio, Resend, Photon, Quo, Dub, Slack, Google or Apple OAuth secrets are present, if Stripe keys aren't test keys, or if the DSN points at the production Supabase project. `CONTACT_HASH_PEPPER` is a plain env var on E2E.

## Gotchas and edge cases

- **Production secret names live on the trigger.** Apart from the migration DSN, deploy Slack webhook, and metrics token, the Secret Manager names bound to production are in the `_RUNTIME_SECRET_REFS` trigger substitution. Check the trigger before assuming a name.
- **`KEY` rotation has no expiry pressure.** Native tokens last 6360 hours, so a legacy key has to stay in `KEY_LEGACY` for months, or every native user is signed out.
- **One Twilio token, three jobs.** Outbound API auth and both inbound webhook validators use `TWILIO_AUTH_TOKEN`. A rotation that updates only one side breaks the others.
- **The OG secret spans two deploys.** The API refuses to start without it, and the worker rejects mismatched signatures, so share previews silently disappear during a one-sided rotation.
- **Metrics and pprof fail closed.** With `METRICS_AUTH_TOKEN` unset, `/metrics` and `/debug/pprof/` aren't mounted at all and the API logs `metrics and pprof endpoints disabled`.
- **The internal key has no scope.** Every `/internal/*` route shares `INTERNAL_API_KEY`, so any new internal route is immediately callable by existing automation.
