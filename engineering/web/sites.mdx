`sites.config.json` registers seven sites. Each one lives in `src/sites/<site>/`, builds to `dist/<site>/`, and deploys to its own Firebase Hosting site in the `yelo-dashboard-v2` project. For how the build works, see [Multisite build](/engineering/web/multisite).

<Warning>
There are no `pay` or `drive` sites. Both folders were removed from `yelo-web`, though the `Makefile` help text still uses `deploy-pay` as an example. Rider tipping, the only web payment flow, now lives in the `signup` site at `/tip/<slug>`, and the `experience-router` Cloudflare Worker serves it at `joinyelo.com/pay/tip`.
</Warning>

## At a glance

| Site | Audience | Auth | Bootstrap | API client | Hosting site ID | Status |
| --- | --- | --- | --- | --- | --- | --- |
| `dashboard` | Admins, interns, fleet managers | Clerk | Bespoke `main.tsx` | `@/generated/dashboard` | `yelo-dashboard-v2` | Live |
| `signup` | Riders and drivers signing up, opening personal invite links, tipping, or deleting accounts | Auth v3 and phone OTP, no Clerk | `renderSite` | `@/generated/signup`, `@/generated/auth-v3` | `yelo-signup` | Live |
| `event` | Anyone with an older shared event link | Public | `renderSite` | `@/generated/event` | `yelo-event` | Live. Event short links now use the `signup` site's `/e/<slug>` landing |
| `home` | Marketing visitors | Public | Plain `createRoot` | None | `yelo-home` | Live |
| `maestro` | Engineers reviewing the product inventory and E2E runs | Public viewer | `renderSite` | Supabase Storage JSON | `yelo-maestro` | Internal |
| `invite` | Anyone opening an `invite.yelo.link` link shared before invites moved to `joinyelo.com/i` | Public | `renderSite` | None | `yelo-invite` | Live |
| `world-cup` | Students in the World Cup campus race | Public | `renderSite` | `@/generated/dashboard` (world-cup functions) | `yelo-world-cup` | Offline. Its public routes redirect to `joinyelo.com` |

The Hosting site IDs come from `.firebaserc`. Each Hosting target has the same name as its site.

## dashboard

The internal operations app for Yelo staff and fleet partners. It is the only site with Clerk authentication and role-based access control.

- **Audience:** `admin`, `intern`, and `fleet` roles. See [Dashboard roles](/administration/dashboard-roles) for what each role can do.
- **Auth:** `ClerkProvider` in `src/sites/dashboard/main.tsx`. Signed-out users see Clerk's `SignIn` with hash routing. `ClerkAxiosInterceptor` adds `Authorization: Bearer <token>` to every request from the shared axios instance.
- **API:** The tag-split React Query client in `src/generated/dashboard/endpoints/`, plus wrapper hooks in `src/hooks/`. The Jobs page embeds River UI in an iframe after minting a cookie through `POST /riverui/session`.
- **Required build variables:** `VITE_API_URL`, `VITE_CLERK_PUBLISHABLE_KEY`, `VITE_MAPBOX_API_KEY`. `VITE_SENTRY_DSN` is optional.
- **Hosting:** Every path rewrites to `/index.html`. HTML is served `no-cache, no-store`, and `/assets/**` is served immutable for one year.

Implementation details are in [Dashboard architecture](/engineering/web/dashboard-architecture). User-facing page guides live under the Dashboard section of these docs, for example [Ride metrics](/dashboard/ride-metrics).

## signup

The public web entry point for account creation and several one-off flows. It has two HTML entries: `index.html` for the main bundle, and `auth/v3/index.html` for Auth v3, so the sign-in page ships without the guest signup bundle.

`src/sites/signup/App.tsx` chooses a flow from the URL path rather than route definitions:

| Path | Flow |
| --- | --- |
| `/auth/v3`, `/auth/v3/callback` | Auth v3 sign-in page (`auth-v3/AuthV3Page`). Normally served by the dedicated entry; the main bundle lazy-loads it as a fallback. |
| `/delete-account` | Account deletion: phone OTP, then confirmation with the word `DELETE`. |
| `/get` | App landing for campaign short links (`get/GetAppPage`). Apple mobile devices go to the App Store with `utm_campaign` as the campaign token, and Android goes to Google Play. Desktop sees **Continue → App Store**, **Continue → Google Play**, and **Continue → web** (Auth v3 with the query string). |
| `/e/<slug>` | Event landing (`event/EventLandingPage`). Loads the event with `usePublicEventGetBySlug` and shows **Get tickets** (the event's `http` or `https` ticket URL, in a new tab) and **Get a ride** (`/get` with the query string, and `utm_campaign=event-<slug>` if none is set). |
| `/i/<code>` | Personal referral invite landing (`invite/InvitePage`). Apple mobile devices go to the App Store with `ct=<code>`. Everyone else sees the landing, which leads with the store for the device: **Continue → Google Play** on Android, carrying the invite as install referrer, and **Continue → App Store** elsewhere. The secondary link, **Continue → web**, goes to Auth v3 with the landing's allowlisted attribution parameters plus the code. |
| `.../tip/<slug>` | Rider tip for a driver or fleet (`TipStep`). If the tip API returns unauthorized, it redirects to Auth v3 with `intent=tip`. `?status=success` shows the confirmation screen. |
| `.../world-cup`, `.../world-cup/claim`, or `?intent=world-cup` | World Cup claim: Auth v3 sign-in, then `.edu` email verification (`EduClaimStep`). The public `joinyelo.com/world-cup/claim` URL now redirects to the home page, so this flow is unreachable in production. |
| Anything else | Redirects into the Auth v3 web flow. |

- **Auth:** No Clerk. Auth v3 uses its own fetch client and a request secret that `captureAuthV3RequestSecret()` strips from the URL before React mounts. Older steps use the Auth v2 phone OTP endpoints.
- **API:** `@/generated/signup` for `authv2`, `tips`, and `user`; `@/generated/auth-v3` for Auth v3; and `worldCupClaimEducationEmail` and `useReferralGetInvitePreview` from the dashboard client. Every page except `/auth/v3` logs a link touch with `POST /authv3/attribution/touch`. See [Signup and Auth v3 site](/engineering/web/signup-and-auth-site#link-landing-touches).
- **Required build variables:** `VITE_API_URL`, `VITE_GOOGLE_WEB_CLIENT_ID`, `VITE_APPLE_SERVICES_ID`. `VITE_APPLE_REDIRECT_URI`, `VITE_AUTH_V3_APP_SCHEME`, `VITE_APP_ENV`, `VITE_POSTHOG_KEY`, and `VITE_POSTHOG_HOST` are optional.
- **Hosting:** Strict security headers and a Content Security Policy on `/auth/v3`, `no-store` on `/delete-account`, `/i/**`, `/get`, and `/e/**`, and `.well-known` app-association files. The `experience-router` Worker proxies `joinyelo.com/auth/v3*`, `/pay/tip*`, `/i/*`, `/get`, and `/e/*` to this site so users see canonical `joinyelo.com` URLs.
- **Link previews:** The build target runs `scripts/emit-signup-html.mjs`, which writes static documents with their own Open Graph tags for `/i/fleet/<code>`, `/get` (the home page card and `og-yelo.png`), and `/e/<slug>` ("Event on Yelo"). A Dub short link with its own card shows that card instead.

<Tip>
In dev, open `/?preview=all` on the signup site to see every step stacked on one page, or `/?preview=<step>` for a single step. For iPhone keyboard testing of Auth v3, run `pnpm dev:signup-device`. See [Local development](/engineering/local-development).
</Tip>

## event

A public landing page for a single event, reached from older shared links. New event short links point at the `signup` site's `joinyelo.com/e/<slug>` landing, which links out to the ticket page instead of embedding Posh checkout.

- **Routes:** `/:slug` renders `EventPage`; anything else shows "Event not found".
- **API:** `usePublicEventGetBySlug` from `@/generated/event`, a client generated only from the public events tags.
- **Features:** A Mapbox static map and directions link, an "open in app" handoff that falls back to `https://yelo.link`, and an embedded Posh checkout (`CheckoutModal`) when the event's ticket URL is a `posh.vip` link.
- **Required build variables:** `VITE_API_URL`, `VITE_MAPBOX_API_KEY`.

## home

The marketing site. It intentionally does not follow the shared conventions: it uses no Tailwind, no `renderSite`, and no router library. `main.tsx` calls `createRoot` directly and switches pages on `window.location.pathname`.

- **Pages:** rider landing (`/`), `/drivers` (also served at the `/drive` alias, which keeps the short link's query string), `/partner`, `/fleets`, `/safety`, `/vision`, `/privacy`, `/tos`, and `/terms`. Each non-root page has a Hosting rewrite to its own `index.html`.
- **`/farefinder`:** The ride price-comparison landing page ("Find the cheapest ride"). It works differently from the other pages. It is a self-contained static HTML, CSS, and vanilla JavaScript page in `src/sites/home/public/farefinder/`, with no React, no route in `main.tsx`, no `firebase.json` rewrite, and no build step. Vite copies `public/` into `dist/home` verbatim, and Firebase Hosting serves the real file before the `**` rewrite. Its images, video, and fonts live under `/farefinder/` so they don't collide with the site's `/img` or `/video`. Every call to action links to `https://yelo.link/aggregator`, which returns a 302 to the App Store listing so taps from this page can be attributed.
- **Assets:** A site-local `public/`. Images in `public/img/` are generated from `assets-src/` by `tools/vite/home/gen-home-images.ts` at build start, and are not committed.
- **Link previews:** The build target also runs `scripts/emit-partner-html.mjs`, which writes static HTML documents with page-specific Open Graph tags because link-preview crawlers do not run JavaScript.
- **API:** None, except that `main.tsx` lazily loads the signup site's touch logger. It records an attribution touch only when the visit carries a click ID, campaign, or referral code, or arrives from another site.
- **Previews:** Pull requests that affect `home` get a Firebase preview channel, and CI comments the URL on the PR.

Read [Home site](/engineering/web/home-site) before you change this site.

## maestro

An internal viewer for the product inventory and for end-to-end test runs. The hostname is historical: no Maestro runs anywhere.

- **Views:** The default view is the product inventory: app screens and their states, joined to test captures. `?view=screens` (the default), `?view=flows`, and `?view=runs` pick the screen gallery, the flow list, and the run list. `?run=<run-id>` opens one run with video, screenshots, and a synchronized action log.
- **Data:** Reads the run index, per-run manifests, and an optional `inventory/catalog.json` as JSON from Supabase Storage, at `VITE_SUPABASE_URL` + `/storage/v1/object/public/e2e`, or from `VITE_E2E_ARTIFACT_BASE_URL` if set. When the bucket has no catalog, the viewer uses the bundled `product-catalog.json`. It does not call the Yelo API.
- **Auth:** None in the viewer. It stores pinned runs and the theme in `localStorage`.
- **Dashboard embed:** The dashboard mounts the same `App` at `/inventory` behind Clerk sign-in and the `admin` role. The artifact bucket and this standalone site stay public. See [Inventory](/dashboard/inventory) and [Public sites](/engineering/web/public-sites#maestro).
- **Hosting:** `**` is served `no-cache, max-age=0, must-revalidate` and `/assets/**` is immutable for a year, so the HTML revalidates and fingerprinted assets cache.
- **Second entry:** `auth/v3/index.html` mounts the signup `AuthV3Page`. The build points `VITE_API_URL` at `VITE_E2E_API_URL` and sets the app scheme to `com.rideyelo.e2e`, so E2E app builds can run the web sign-in flow against the E2E API.
- **Required build variables:** `VITE_SUPABASE_URL`, `VITE_E2E_API_URL`.

## invite

Forwards personal and fleet invite links shared before invites moved to `joinyelo.com/i`. It no longer renders an invite page.

- **Routes:** An inline script in `index.html` redirects `/<code>` to `https://joinyelo.com/i/<code>` and `/fleet/<code>` to `https://joinyelo.com/i/fleet/<code>`, with the query string, before the bundle loads. The root path redirects (302) to `https://joinyelo.com/`. Any other path renders "Invite not found".
- **Where invites live:** Both landings are in the `signup` site (`src/sites/signup/invite/`), so their attribution cookies are first-party to sign-up. See [Public sites](/engineering/web/public-sites#invite).
- **API:** None. `FleetInvitePage` and its `useFleetJoinGetPreview` call moved to the `signup` site.
- **App links:** The Vite config emits an `apple-app-site-association` file with invite-specific path components so invite paths open the app.
- **Analytics:** Dub, through `renderSite({ dubAnalytics: true })`.
- **Required build variables:** `VITE_API_URL`.

For the fleet invite flow from the operator's side, see [Driver invitations](/fleets/driver-invitations).

## world-cup

The campus race landing page: a live leaderboard, map, and signup ticker for the listed campuses.

<Warning>
The World Cup site is offline. The `world-cup-router` Worker answers `/world-cup*` on `rideyelo.com` and `joinyelo.com`, including `/world-cup/claim` and `/world-cup/api`, with a 302 to `https://joinyelo.com/`. The site and its Firebase Hosting target stay in place. Only the proxy is removed, so you can restore it from git history.
</Warning>

- **Serving:** Builds with `base: '/world-cup/'`. While the campaign ran, the `world-cup-router` Cloudflare Worker served it at `rideyelo.com/world-cup*` and `joinyelo.com/world-cup*` and let every other path fall through to Framer.
- **API:** `worldCupGetStandings` and `worldCupGetActivity` from the dashboard client, called through the same-origin `/world-cup/api` prefix. It polls activity with a cursor.
- **Claim flow:** Claim links point at `VITE_SIGNUP_URL`, which defaults to `https://joinyelo.com/world-cup/claim` and is handled by the `signup` site.
- **Required build variables:** None. `VITE_SIGNUP_URL` is a cache input.

See `src/sites/world-cup/README.md` for ticker and standings behavior.

## Cloudflare Workers

Three Cloudflare Workers in `workers/` sit in front of some sites. They deploy separately from Firebase:

| Worker | Routes | Purpose |
| --- | --- | --- |
| `experience-router` | `joinyelo.com/*`, `www.joinyelo.com/*` | Proxies `/auth/v3`, `/pay/tip*`, `/i/*`, `/get`, `/e/*`, and `/_yelo/signup/*` to the `signup` site origin (`yelo-signup.web.app`). Every other path passes through to the home site. Plants attribution cookies on link landings. |
| `world-cup-router` | `rideyelo.com/world-cup*`, `joinyelo.com/world-cup*` | Redirects every World Cup path (302) to `https://joinyelo.com/`. Its longer pattern wins over the experience router. Other paths, such as `/world-cupcake`, pass through. |
| `og` | `rideyelo.com/og/*` | Renders signed Open Graph images for invite, fleet, event, and tip links. |

### Attribution at the edge

The `experience-router` Worker sets two first-party cookies on attributed landings: `yelo_attr`, the entry click (Dub click ID, UTM parameters, channel, and referral code), and `yelo_anon_id`, an anonymous ID. Both use `Domain=.joinyelo.com; Path=/; Max-Age=7776000; SameSite=Lax; Secure`, so they last 90 days. Response cookies aren't subject to Safari's seven-day cap on script-written cookies.

- Signup landings (`/pay/tip*`, `/i/*`, `/get`, `/e/*`) always get a `yelo_anon_id` if the visitor has none, and a `yelo_attr` entry when the URL carries attribution.
- Other `joinyelo.com` pages, including the home page, get cookies only on a `GET` with a query string that carries attribution and an HTML response. Requests without a query string, and non-`GET` requests, pass through untouched.
- `/auth/v3` never gets these cookies. Its callback's `code` is an OAuth code, not a referral code.
- A failure while planting cookies serves the page anyway.

At sign-up, Auth v3 fills missing attribution fields from `yelo_attr`. See [Growth features](/concepts/growth-features#attribution-cookies).

Run `pnpm worker:<name>:check` before you merge a Worker change. Deployment details are in [Deployment](/engineering/deployment).
