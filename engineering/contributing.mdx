The three repositories share one workflow: branch from `main`, run the local gate, open a pull request, and merge after CI passes. Merging to `main` deploys the API and the web sites automatically, so treat every merge as a release.

## Branches

- Branch from `main` and name the branch `<owner>/<topic>`, for example `carter/canonical-top-locations`. Include the Linear issue when there is one: `harryxu497/yelo-1265-remove-coming-tag`.
- Automation owns these prefixes. Don't push to them by hand:
  - `automation/update-openapi-contract`: contract updates from `yelo-api`. See [OpenAPI and generated clients](/engineering/openapi-and-clients).
  - `backport/<version>-sync`: rolling mobile release-branch syncs.
- In `yelo-frontend`, version-named branches such as `5.7.3` are release branches. Only OTA-safe backports land there. See [mobile releases](/engineering/mobile/releases).

## Commit subjects and pull request titles

Use a kernel-style subject: a lowercase area prefix, a colon, and a specific, lowercase summary. Most pull requests squash-merge with the pull request title as the commit subject, so the title is what lands in history.

```text
dashboard: filter confirmed unmatched rides and classify outcomes
ride: harden state snapshots and lifecycle transitions (yelo-1271)
mapping: rank poi enrichment by location and name (yelo-1279)
fleet join: support owner-operator enrollment
```

- Pick the area from the domain you changed, such as `ride`, `dashboard`, `mapping`, `authv3`, `fleet join`, or `deps`.
- Append the Linear identifier in parentheses when one exists. Don't invent one.
- Keep the summary imperative and technical. Say what changed, not how you felt about it.

Bots use their own formats. The OpenAPI bot writes `chore(api): update OpenAPI contract to <sha>`. Dependabot uses `deps` in `yelo-api` and `build(deps)` in `yelo-web`.

## Pull request descriptions

Write the description as bullet points that cover:

- what changed and why
- breaking changes, including removed or renamed API fields
- required non-code configuration, such as new environment variables, Secret Manager entries, GitHub variables, EAS environment values, or Firebase Hosting sites
- database migrations: the schema change, any data backfill, and whether the migration is safe while the previous revision still serves traffic
- for `yelo-frontend`, whether the change is OTA-safe or needs a store build

Leave out procedural chatter, conversation history, and commentary.

<Warning>
In `yelo-frontend`, changes to `package.json`, the lockfile, `app.json` or `app.config.ts`, `eas.json`, `patches/`, or native modules need a new store build and a human release decision. Put them in their own pull request and say so in the description.
</Warning>

## Before you push

Run the full gate for the repository you changed. It is the same set of checks CI runs.

<Tabs>
  <Tab title="yelo-api">
    ```bash
    make check
    ```
    `pre-commit install` wires `make check` into a Git pre-commit hook, so it runs on every commit. It covers migration policy, generated code (OpenAPI, sqlc, mocks), lint, unit and integration tests, and the merged coverage floor. Integration tests need Docker.

    For a faster inner loop, use `make a`. It runs `go mod tidy`, regenerates mocks, runs lint with auto-fix, and runs `make tf`. `make a` does not check the OpenAPI contract, sqlc output, migration policy, or coverage floor, so still run `make check` before you push.

    If you change handlers or DTOs, run `make openapi`. If you change queries, run `make sqlc-generate`. If you change a mocked interface, run `make mocks`. Stage any new generated files before you run the checks. The checks reject untracked generated output.
  </Tab>
  <Tab title="yelo-web">
    ```bash
    pnpm nx run workspace-quality:ci
    pnpm format   # write formatting fixes
    ```
    If you touched a site's `firebase.json` or added a site, run `pnpm firebase:config` too. If you changed a worker, run `pnpm worker:<name>:check`.
  </Tab>
  <Tab title="yelo-frontend">
    ```bash
    make fix     # safe oxlint fixes, oxfmt, vehicle catalog regeneration
    make check   # api-check, fmt-check, typecheck, lint, lint-types, test
    ```
    Typed routes are generated by Metro into `.expo/types/router.d.ts`. Run `make dev` once so `make typecheck` can check route strings locally.
  </Tab>
</Tabs>

See [testing](/engineering/testing) for what each gate covers.

## Lint rules you will hit

### Go

`.golangci.yml` enables a broad linter set. These thresholds fail the build:

| Linter | Limit |
| --- | --- |
| `gocyclo` | Cyclomatic complexity 15 |
| `gocognit` | Cognitive complexity 30 |
| `funlen` | 200 lines or 100 statements, comments ignored |
| `nestif` | Nesting complexity 5 |
| `dupl` | 150 tokens |

Other rules to know:

- `forbidigo` bans `fmt.Print*`, `print`, and `println`. Use the structured logger.
- `nolintlint` requires every `//nolint` to name the specific linter and give a reason, for example `//nolint:gocyclo // initialization registers every metric`. Unused suppressions fail.
- Linters also enforce checked errors and type assertions, error wrapping, context propagation, closed resources, exhaustive switches, and `wsl_v5` whitespace rules.
- Use the error types in `internal/utilities/errors` (`errors.Wrap`, `errors.NewServerError`) for errors that reach handlers and the logger.

Pinned tool versions live in the `Makefile`: golangci-lint 2.13.2, sqlc 1.31.1, mockery 3.7.0. Update them by hand. Dependabot doesn't manage them.

### TypeScript

Both frontends use oxlint and oxfmt, with ESLint kept only for React Hooks and React Compiler rules. Mobile-specific rules that lint enforces:

- No `console.*`. Use `log` from `@/lib/observability/logger`.
- `components/design-system/` must not import feature code, providers, hooks, or stores.
- Import `expo-haptics` only through `lib/platform/haptics`. Use Phosphor icons, never `@expo/vector-icons`. Import `date-fns` by subpath.
- No pure white or black hex literals outside map layers. Add a theme token first.
- Use `import type` for types. No non-null assertions. No `as never` on routes.

See [mobile architecture](/engineering/mobile/architecture) and [dashboard architecture](/engineering/web/dashboard-architecture) for the conventions behind these rules.

## Code review

- `yelo-api/.github/CODEOWNERS` requires `@rideyelo/migration-approvers` to review anything under `migrations/`. Applied migrations are immutable, so add a new migration instead of editing one.
- Review OpenAPI bot pull requests like any other change. Type errors there are the first sign of a breaking contract change.
- For mobile, reviewers confirm the OTA classification. The **Fingerprint** check comments when native inputs changed.
- Leave comments only for non-obvious logic. Keep them to one line, two at most.

## Dependencies

Dependabot opens weekly updates in every repository. None are merged automatically.

| Repository | Ecosystems | Notes |
| --- | --- | --- |
| `yelo-api` | Go modules, GitHub Actions | Action SHA pins included |
| `yelo-web` | npm, GitHub Actions | Minor and patch updates grouped |
| `yelo-frontend` | npm | Expo-managed packages such as `expo-*`, `react`, and `react-native` are ignored. Upgrade them with `npx expo install --fix` during SDK upgrades |

A dependency update in `yelo-frontend` changes the lockfile, so it is not OTA-safe. It needs a store build and a human release decision.

GitHub Actions in `yelo-api` and `yelo-web` are pinned to commit SHAs, and both repositories include an `actionlint.yaml` config for workflow linting.
