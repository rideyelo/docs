---
title: "Add a web site"
description: "Recipe for a new yelo-web site: scaffold it with make new-site, declare build inputs, give it an API client, create the Firebase Hosting target, allow its origin in the API, and route a public hostname or path to it through Cloudflare."
---

Every public web property except the marketing site on Framer is a site in `yelo-web`. It's one Vite project that builds into many Firebase Hosting sites. [Multisite build](/engineering/web/multisite#add-a-new-site) covers the scaffold and Firebase steps. This recipe covers the whole path to a live URL, including the API and edge changes that live outside `yelo-web`.

## Worked examples

| PR | What it shows |
| --- | --- |
| [yelo-web#27](https://github.com/rideyelo/yelo-web/pull/27) | Registers `src/sites/home/` in `sites.config.json` so the standard `SITE=home make dev`, `make build-site`, and `make deploy-home` targets work. Switches its Hosting config to the SPA rewrite. The Firebase site and domain were unchanged. |
| [yelo-web#130](https://github.com/rideyelo/yelo-web/pull/130) | A Hosting-only change: `src/sites/invite/firebase.json` redirects, regenerated into the root `firebase.json`. |
| [yelo-web#20](https://github.com/rideyelo/yelo-web/pull/20) | A new Cloudflare Worker (`workers/og`) with its own `wrangler.jsonc`, deployed separately from any site. |

## Recipe

<Steps>
  <Step title="Scaffold the site">
    ```bash
    make new-site NAME=widgets
    ```

    `scripts/new-site.mjs` copies `scripts/templates/site/` into `src/sites/widgets/`, appends `widgets` to `sites.config.json`, and regenerates the root `firebase.json`. The template's `project.json` is tagged `firebase-site`, which is how CI finds deployable sites. Its `firebase.json` rewrites every path to `/index.html`.
  </Step>
  <Step title="Run it">
    ```bash
    SITE=widgets make dev
    ```

    The template renders through `renderSite(<App />, { query: true, toaster: true })`: a public page with React Query and a toaster. For auth, wrap the app in `ClerkAuth` and pass `router: true`. See [Dashboard roles](/administration/dashboard-roles) for Clerk.
  </Step>
  <Step title="Declare build variables">
    In `src/sites/widgets/project.json`, list every `VITE_*` variable the site reads in `metadata.requiredBuildEnv` and as `{ "env": "..." }` build inputs. The invite site's `project.json` is a minimal example with `VITE_API_URL`.

    The deploy workflow's **Require affected site build variables** step fails when a listed variable is empty. Add any new variable as a GitHub repository variable, and to the top-level `env` blocks in both `.github/workflows/ci.yml` and `.github/workflows/firebase.yml`.
  </Step>
  <Step title="Give it an API client, if it calls the API">
    Call the API through a generated client. ESLint blocks importing `@/lib/api-client` anywhere under `src/`, and blocks raw `fetch` in `src/components`, `src/hooks`, and the dashboard site. Either import from an existing generated client, or add a narrow one to `orval.config.ts` with an `include` tag filter, as `event` does:

    ```ts
    widgets: {
      input: { target: './docs/openapi.json', filters: { mode: 'include', tags: ['Widgets'] } },
      output: {
        mode: 'tags-split',
        target: './src/generated/widgets/endpoints',
        schemas: './src/generated/widgets/models',
        client: 'react-query',
        httpClient: 'axios',
        override: { useTypeOverInterfaces: true, mutator: { path: './src/lib/api-client.ts', name: 'customInstance' } },
      },
    },
    ```

    Then run `make orval` and `make api-check`, and commit `src/generated/widgets`. See [OpenAPI and clients](/engineering/openapi-and-clients).
  </Step>
  <Step title="Tune Hosting behavior">
    Edit `src/sites/widgets/firebase.json` for headers, CSP, redirects, and rewrites. Keep `target` and `public` as generated. Then regenerate and check the root file:

    ```bash
    pnpm firebase:config
    pnpm firebase:config:check
    ```

    See [Firebase Hosting rules per site](/engineering/web/edge-and-routing#firebase-hosting-rules-per-site) for existing CSPs to copy from.
  </Step>
  <Step title="Create the Hosting site and target">
    Someone with access to the `yelo-dashboard-v2` Firebase project runs this once:

    ```bash
    firebase hosting:sites:create yelo-widgets --project yelo-dashboard-v2
    firebase target:apply hosting widgets yelo-widgets --project yelo-dashboard-v2
    ```

    Commit the `.firebaserc` change. Hosting site IDs are global. If `yelo-widgets` is taken, pick another ID and keep the target name `widgets`.
  </Step>
  <Step title="Allow the origin in the API">
    If the site calls `yelo-api` from the browser, add both its `*.web.app` origin and its custom domain to the defaults in `corsTrustedOrigins()` in `yelo-api/internal/utilities/config/config.go`. Add them to `CORS_TRUSTED_ORIGINS` in `.env.example` too.

    If production sets `CORS_TRUSTED_ORIGINS` on the release trigger, that list replaces the defaults, so update the trigger value as well. Auth v3 routes use a separate origin list (`AUTH_V3_CORS_ORIGINS`).
  </Step>
  <Step title="Merge and deploy">
    Merging to `main` builds and deploys every affected `firebase-site` project through `.github/workflows/firebase.yml`. To deploy by hand, run `make deploy-widgets`, which builds the site and runs `firebase deploy --only hosting:widgets`.
  </Step>
  <Step title="Point a hostname or path at it">
    Pick one:

    - **A dedicated hostname** such as `widgets.yelo.link`: add it as a custom domain on the Hosting site in the Firebase console, and create the DNS records Firebase asks for wherever that zone's DNS is hosted. The repo doesn't record how the existing custom domains were set up.
    - **A path on an existing hostname** such as `joinyelo.com/widgets`: route it through a Worker. Add `routes` entries with `pattern` and `zone_name` in the Worker's `wrangler.jsonc`, and proxy to the site's `*.web.app` origin. `world-cup-router` is the simplest model. Workers deploy by hand with `pnpm worker:<name>:deploy`, not from CI.

    [Edge and routing](/engineering/web/edge-and-routing) describes how the existing Workers rewrite `Location` headers and namespace assets. A path-mounted SPA needs the same treatment.
  </Step>
  <Step title="Document it">
    Add the site to [Sites](/engineering/web/sites) with its purpose, audience, auth model, and Hosting target, and add any hostname to [Deep links and URLs](/reference/deep-links-and-urls).
  </Step>
</Steps>

## Checklist

- [ ] `sites.config.json`, `src/sites/<name>/`, and the root `firebase.json` are committed together.
- [ ] Every `VITE_*` input is in `requiredBuildEnv`, the build inputs, GitHub variables, and both workflow `env` blocks.
- [ ] API calls go through a generated client, and the API allows the site's origins.
- [ ] `.firebaserc` maps the target to a created Hosting site.
- [ ] The hostname or Worker route is live and serves the latest deploy.
- [ ] The Sites page is updated.

## Gotchas and edge cases

<AccordionGroup>
  <Accordion title="The first deploy fails without a target mapping">
    CI deploys every affected site. If `.firebaserc` has no `hosting` target for the new name, `firebase deploy --only hosting:<name>` fails. Create the site and apply the target before you merge.
  </Accordion>
  <Accordion title="Path-mounted sites and asset URLs">
    A Vite build references `/assets/...` from the site root. Served under `joinyelo.com/widgets`, those requests hit the parent origin instead. `experience-router` solves this by rewriting asset URLs to `/_yelo/signup/...` and proxying them, and by returning 404 when Firebase answers an asset request with its SPA `index.html`. A new path mount needs the same handling.
  </Accordion>
  <Accordion title="Nx only rebuilds affected sites">
    `docs/**` is in `.nxignore`, so a contract sync alone doesn't rebuild every site. If the new site imports a shared library through a path Nx can't infer, add it to `implicitDependencies`, or changes to it won't redeploy the site.
  </Accordion>
</AccordionGroup>
