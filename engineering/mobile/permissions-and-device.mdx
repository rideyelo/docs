This page lists every OS permission and device capability `yelo-frontend` touches. It covers the native config (`app.json`, `app.config.ts`), the runtime prompts, the fallback UI when a user says no, and the device data the app reports back to the API.

For how location feeds heartbeats and the driver background task, see [Rider and driver flows](/engineering/mobile/rider-and-driver-flows#location). For release impact, remember that every item in the native config section below is a store-build change. See [Releases](/engineering/mobile/releases#ota-versus-native-rebuild).

The first tap re-prompts, later taps open Settings. |

## Onboarding permissions screen

`app/(auth-v3)/permissions.tsx` is the only place the app asks for several permissions together. It renders **Yelo needs some permissions** with three `PermissionsCard` rows (Location, Notifications, Contacts) and a **Finish** button.

<Steps>
  <Step title="Silent check">
    On mount it reads all three statuses without prompting. `areOnboardingPermissionsGranted` in `lib/auth/permissions.ts` returns true only when location and contacts are `granted` and notifications count as allowed. If all three pass, the screen calls `completePermissions()` and never renders.
  </Step>
  <Step title="Auto-request after 2 seconds">
    If anything is missing, the screen renders and schedules `onContinue` after 2,000 ms. The user does not have to tap **Finish**. Tapping **Finish** early cancels the timer and runs the same flow.
  </Step>
  <Step title="Sequential native prompts">
    `onContinue` asks for location, then notifications, then contacts, one at a time "so iOS never has to coordinate overlapping prompts". Each step emits `auth_v3_permission_requested` and `auth_v3_permission_completed` with `outcome: granted | denied`.
  </Step>
  <Step title="Location is the only hard gate">
    Notification and contact failures are non-fatal. If location is denied, the screen shows "Location access is required before you can open the map." with an inline **Open Settings** link, and stays put.
  </Step>
</Steps>

<Note>
On iOS, "notifications allowed" means `granted` plus `allowsAlert`, `allowsBadge`, and `allowsDisplayInNotificationCenter`. A provisional or banner-only grant counts as denied. On a simulator (`Device.isDevice` false) notifications always count as allowed.
</Note>

## Location

### Foreground

`providers/LocationProvider.tsx` owns foreground permission and the single `watchPositionAsync` client.

- `checkPermissions(false)` runs on mount and on every return to the foreground. It never prompts.
- `requestPermissions()` prompts only if `canAskAgain` is true. Otherwise it sets `errorMsg` to "Location permission denied. Please enable it in Settings." and returns false.
- `permissionsChecked` stays false until the first silent check settles, so gates never flash.
- Revoking permission calls `controller.reset()` to drop the cached fix and ignore late native callbacks.
- On any screen where `inSensitiveFlow` is true (active ride or drive paths), the provider forces `trackLocation` on and calls `checkPermissions(true)`, which can prompt.

The UI surfaces for a missing grant:

| Surface | File | Behavior |
| --- | --- | --- |
| Map blocker | `components/map/LocationGate.tsx` | Absolute overlay at `zIndex: 1000`: **Turn on location**, "Yelo is built around where you are — rides, friends, and spots near you. Enable location to use the map." Button reads **Enable location**, then **Open Settings** after one failed request. Hidden while the request sheet is active. |
| Onboarding | `app/(auth-v3)/permissions.tsx` | Inline "Location access is required…" with **Open Settings**. |
| Legacy search pill | `components/home/WhereTo.tsx` | Native alert **Location Required** with **Not Now** and **Open Settings**. The component is exported but no screen renders it. |
| Save location, events, deals | `save-location/index.tsx`, `events/[eventId]`, `deals/[dealId]` | Call `requestForegroundPermissionsAsync()` directly for a best-effort ETA and silently skip on denial. |

The app never distinguishes precise from approximate location. It does not read `accuracy` authorization on iOS 14+ or `ACCESS_COARSE_LOCATION`-only grants on Android. A coarse grant counts as `granted`.

### Background ("Always")

<Warning>
No code calls `requestBackgroundPermissionsAsync()`. The app only reads the background status.
</Warning>

When a driver taps **Go online**, `handlePressGoOnline` in `app/(app)/drive/index.tsx` calls `Location.getBackgroundPermissionsAsync()`:

- `granted`: the go-online confirmation sheet opens.
- Anything else, or a thrown error (older Android binaries without the manifest capability throw): `LocationRequiredSheet` opens.

`components/drive/LocationRequiredSheet.tsx` shows **Keep your driver location updated**, explains that "Yelo collects your location in the background while you're online as a driver, even when the app is closed", and instructs "open Settings → Yelo → Location and choose 'Allow all the time' or 'Always'". **Open Settings** calls `Linking.openSettings()`. **Not now** dismisses.

So every driver must upgrade to Always in system Settings by hand. On iOS the app never triggers the system "Change to Always Allow" upgrade prompt.

### Background task and foreground service

`tasks/DriverLocationTask.ts` runs only while the driver is online or has a current ride. Relevant device settings:

| Setting | Value |
| --- | --- |
| Accuracy | `Balanced` |
| Interval | 15 s, 25 m, deferred to the same values |
| Activity type | `AutomotiveNavigation`, `pausesUpdatesAutomatically: false` |
| iOS indicator | `showsBackgroundLocationIndicator: true` (blue status bar pill) |
| Android foreground service | Title "Location sharing active", body "Updating your location for your ride", icon `assets/yelo/notification-icon.png` from the `expo-location` plugin |

The task self-heals after a force-quit: iOS relaunches the app for significant location changes, and the task unregisters itself if the SecureStore flag `driver_should_share_location` is not `1`.

## Notifications

- **Prompt.** `PushNotificationProvider.requestPermissions()` calls `registerForPushNotificationsAsync(true)`. Only two screens call it: Auth v3 permissions and `post-signup/10-marketing` (both **Continue** and **Interested in driving**).
- **Token registration.** Separately, once a JWT exists and the app is interactive, the provider fetches an Expo push token without prompting and posts it to `POST /notification/set-token` only if it changed. Simulators never register a token.
- **Android channels.** `default` ("Yelo notifications") and `kaching-channel` ("Kaching", sound `kaching.wav`), both `HIGH` importance. They are created lazily inside registration, not at startup.
- **Foreground display.** Banner, list, and sound are shown unless `data.type` is `map_content_changed`. The badge is never set.
- **Denied.** Nothing in the app re-prompts or deep-links to notification settings. Settings exposes an in-app **Notifications** toggle (`NotificationsSheet`) that writes `PUT /user/allow-notifications`, which is a server preference, not the OS permission.

## Contacts

`providers/ContactPermissionProvider.tsx` wraps `expo-contacts`.

- It tracks `status`, `accessPrivileges` (`all`, `limited`, `none`), and `canAskAgain`, and bumps `permissionRevision` whenever that signature changes. On iOS, a `limited` grant also bumps the revision on every foreground, because the selected people can change in Settings without a status change.
- `requestPermissions()` prompts only when `canAskAgain` is true.
- `manageContactAccess()` picks the right action: prompt if possible, `Contacts.presentAccessPicker()` when access is `limited`, otherwise `Linking.openSettings()`. iOS has no public URL for the Contacts subsection, so it lands on the app's Settings page.
- Reads re-check permission after the native call. If access changed mid-read, the read throws "Contact access changed while reading" so a revoked book never repopulates.

The permission string (from `app.config.ts`) is: "Yelo securely sends phone numbers from your contacts to Yelo to find people you know. Contact names and other details are not uploaded." For what is uploaded and how, see [Social and contacts](/engineering/mobile/social-and-contacts#contacts-sync).

### Android manifest

- Declared permissions: `ACCESS_NETWORK_STATE`, `ACCESS_FINE_LOCATION`, `ACCESS_COARSE_LOCATION`. Plugins add background location, foreground service, camera, contacts, and notification permissions.

- Non-E2E builds add a `uberauth` intent filter for the Uber login callback.

### Store review and feedback prompt

`providers/FeedbackPromptProvider.tsx` runs a custom three-step funnel: **Thoughts on the app?** (Meh or Love it!), **What can we improve?** (Not Now or Give Feedback), then a free-text modal. Whatever the user picks, finishing the funnel calls `maybeRequestReview`, which calls `StoreReview.requestReview()` if the 90-day native cooldown allows.

| Trigger | Caller | Custom funnel cadence |
| --- | --- | --- |
| `ride-positive` | `ride-complete` after a 4 or 5 star rating | 1st positive rating, then every 10th, 14-day cooldown |
| `first-like` | Liking a spot in `SearchOverlay` | Once |
| `driver-shift` | Going offline after 3+ positive and 0 negative rider ratings this shift | 14-day cooldown |
| `driver-approved` | `(app)/_layout.tsx` on `driver_application_status` change | Once |

Feedback text goes only to PostHog as `appFeedbackSubmitted` with the full `text`. It is not sent to the Yelo API.

- **The store prompt has its own cadence.** `maybeRequestReview` (`lib/prompts/reviewPrompt.ts`) keeps a separate per-user `reviewPrompt:<userId>` record. For `ride-positive` it counts every call and continues only on the 1st and every 10th, and `first-like` and `driver-approved` fire once each. Because it counts only finished funnels, the native prompt can lag the custom funnel's cadence.
- **Dismissing the first dialog skips the store prompt.** Dismissing **Thoughts on the app?** calls `reset`, not `finish`, so `maybeRequestReview` never runs. Declining on **What can we improve?** or the text modal still finishes the funnel.

For client toggles and experiment gates that sit next to these prompts, see [Widgets, experiments, and client toggles](/engineering/mobile/widgets-and-experiments).

### Telemetry payload

`lib/observability/TelemetryService.ts` posts `POST /telemetry/` at most every 5 minutes (forced on contact-permission changes). It includes platform, OS version, device model and manufacturer, native app version and build, `expo_update_id`, screen size and pixel ratio, locale and timezone, `notifications_enabled`, `location_permission` (`always`, `when_in_use`, `denied`, `undetermined`), contact status and access scope, the Expo push token, carrier, total memory, and the Android install referrer.

## Gotchas and edge cases

- **Drivers must find "Always" themselves.** The app never requests background location, so every new driver hits `LocationRequiredSheet` on their first **Go online** and must change the setting in the Settings app.
- **Waze never opens on iOS.** `openNavApp` in `components/drive/CurrentRideBottomSheet.tsx` probes `waze://` with `canOpenURL`, but `waze` is not in `LSApplicationQueriesSchemes`, so iOS returns false and the app falls back to the Google Maps web URL. Android has the same issue: the manifest `<queries>` block lists only the ride-provider schemes.
- **Two camera strings compete.** Both `expo-image-picker` and `expo-camera` write `NSCameraUsageDescription`. The one applied last wins at prebuild. Check the generated `Info.plist` before submitting a build.
- **`msauth://` probe is unlisted.** `lib/auth/oAuth.ts` checks for Microsoft Authenticator with `canOpenURL('msauth://')`, which isn't in `LSApplicationQueriesSchemes`, so it always returns false on iOS.
- **Notifications have no recovery path.** A user who denies notifications during onboarding is never asked again and never sent to Settings.
- **Notification channels exist only after registration.** They are created inside `registerForPushNotificationsAsync`. A push that arrives before that uses the OS default channel.
- **Ride alerts are foreground-only.** `playRideAlert` returns early unless the app is active, and `expo-audio` has background playback disabled. A backgrounded driver relies on the push sound.
- **Coarse location counts as granted.** A user who picks approximate location passes every gate, but pickup accuracy suffers.
- **Deals and events prompt out of context.** Opening an event or deal detail calls `requestForegroundPermissionsAsync()` just to show an ETA.
- **`userInterfaceStyle` is `automatic`** in `app.json`, but the app ships only a light theme. System dark mode affects native chrome (alerts, pickers) but not app screens.
