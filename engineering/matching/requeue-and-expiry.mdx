A ride can return to `confirmed` after it was assigned, and a `confirmed` ride can be retired without a driver. This page covers those paths. For cancellations that end a ride, see [Cancellations](/concepts/cancellations).

## Paths back to `confirmed`

| Path | Trigger | Code |
| --- | --- | --- |
| Driver-cancel requeue | The assigned driver cancels from `queued`, `driver_en_route`, or `driver_waiting` | A `cancel` ride operation with `requeue` set (`RideCancellationCommands`) |
| Offline unqueue | A driver with queued rides has no presence and no ping for 5 minutes | `UserService.unqueueOfflineDriverRides` |
| Direct-request release | Selected driver declines, or the 30-second hold lapses | `DeclineRide`, `resumeExpiredDirectRide` |

Direct-request release never leaves `confirmed`, so it only clears the hold. See [Direct requests](/engineering/matching/direct-requests).

## Driver-cancel requeue

`RideService.Cancel` forwards every cancellation to the ride financial runtime as a `cancel` operation. See [Ride operation journal](/engineering/payments/ride-operation-journal#cancel). `freezeCancellation` in `internal/data/repository/ride_cancellation_operation.go` decides whether it's a requeue:

```go
inputs.Requeue = role == models.UserTypeDriver && slices.Contains([]models.RideStatus{
	models.RideStatusQueued, models.RideStatusDriverEnRoute, models.RideStatusDriverWaiting,
}, inputs.Status)
```

A requeue always has a zero fee. A driver cancel from `in_progress` isn't a requeue, and ends the ride.

<Steps>
  <Step title="Reserve">
    `CancelLegacy` finds the driver's current cancellation quote, or creates a zero-fee one, and reserves the operation under the ride command locks. No ride column changes yet. The unresolved operation blocks every other command on the ride.
  </Step>
  <Step title="Void the hold">
    If the ride has a `payment_intent_id`, the `void` step cancels it at Stripe and records the receipt. A ride without a hold skips this.
  </Step>
  <Step title="Reset in one transaction">
    `Finalize` retakes the locks, verifies the void receipt, and runs `RequeueReservedRide`. In the same transaction, `PromoteNextQueuedRide` promotes the cancelling driver's next queued ride, if any, and reserves that ride's `promotion` operation. The revision finalizer runs for both rides. The transaction also inserts the `auto_requeued` ride event, enqueues the rider's `ride_requeued` push, and finishes the operation.
  </Step>
  <Step title="Reconcile the board and queue">
    The `ride_operation` job runs `ReconcileRideOperation`. The ride is `confirmed`, so it's added to the board, and the cancelling driver's queue summary is refreshed.
  </Step>
  <Step title="Notify drivers">
    The same job calls `dispatchRematchedRide`, which sends `ride_available` to the ride's T0 targets with the event key `ride_available:{rideId}:rematch:{lifecycleRevision}` and adds them to the notified-drivers cache.
  </Step>
</Steps>

Steps 4 and 5 retry until they succeed. The job isn't acknowledged until both are done. See [Terminal effects](/engineering/payments/ride-operation-journal#terminal-effects).

The reset:

```sql
UPDATE "Rides" SET status='confirmed',driver_id=NULL,driver_vehicle_id=NULL,
 payment_consent_at=COALESCE(payment_consent_at,confirm_time),confirm_time=clock_timestamp(),
 match_time=NULL,offer_time=NULL,potential_driver=NULL,auto_queued=false,
 at_pickup_time=NULL,pickup_time=NULL,complete_time=NULL,
 pickup_distance=NULL,pickup_duration=NULL,pickup_route=NULL,
 payment_intent_id=NULL,payment_intent_client_secret=NULL,stripe_merchant_id=NULL,
 cloned_payment_method_id=NULL,pre_auth_amount=NULL,
 declined_drivers=array_append(declined_drivers,sqlc.arg(driver_id)::uuid),
 cancel_reason=sqlc.arg(reason)::text,cancel_comment=sqlc.arg(comment)::text,
 cancel_user=NULL,cancel_phase=NULL
WHERE id=sqlc.arg(ride_id)::uuid;
```

## What each path resets

| State | Driver-cancel requeue | Offline unqueue |
| --- | --- | --- |
| `status` | `confirmed` | `confirmed` |
| `driver_id`, `driver_vehicle_id`, `match_time` | Cleared | Cleared |
| `fleet_id` | Kept | **Cleared to null** |
| `auto_queued` | Cleared | Cleared |
| `confirm_time` | **Reset to now** | Kept |
| `payment_consent_at` | Set to the old `confirm_time` if null | Unchanged |
| `declined_drivers` | Driver appended | Unchanged |
| `potential_driver`, `offer_time` | Cleared | Unchanged |
| `cancel_reason`, `cancel_comment` | Set to the driver's values | Unchanged |
| `pickup_distance`, `pickup_duration`, `pickup_route` | Cleared | Kept (stale) |
| `at_pickup_time`, `pickup_time`, `complete_time` | Cleared | Unchanged |
| `payment_intent_id`, `payment_intent_client_secret`, `stripe_merchant_id`, `cloned_payment_method_id`, `pre_auth_amount` | Cleared, after the hold is voided | Kept |
| `price`, `discounted_price`, `confirm_code`, `payment_method_id` | Kept | Kept |
| `lifecycle_revision` | Incremented | Incremented |
| `assignment_generation` | Incremented | Incremented |
| Board entry | Added by the operation's job | Added |
| T0 push | Sent by the operation's job, once per requeue | None |
| Rider push | `ride_requeued`, enqueued in the requeue transaction | None |
| Queue summary | Refreshed by the operation's job | Deleted |

Neither path clears the ride's matching keys in Redis. A driver-cancel requeue adds its T0 targets to `ride:notified:{rideId}`.

| Key | Effect after requeue |
| --- | --- |
| `ride:notify:{rideId}` (20 min) | Tiers already fired don't fire again. With a reset `confirm_time`, the next tier waits for its full delay from the requeue |
| `ride:notified:{rideId}` (30 min) | Drivers notified before are still excluded from tiers without `ignore_already_notified` |
| `ride:aq_attempted:{rideId}` (1 h) | If an earlier pass gave up, the requeued ride skips auto-queue |
| `ride:rescue:{rideId}` (30 min) | A rescue alert already sent isn't sent again |
| `driver:activation_cd:{driverId}` | Unrelated to the ride. Previously paged drivers stay in cooldown |

### Payment on the next accept

A driver-cancel requeue leaves no hold behind, so the next `accept` clones the payment method and authorizes on the new driver's account like a first accept.

Offline unqueue keeps `payment_intent_id`. A ride accepted into a queue has no hold yet, so there's usually nothing to keep. When there is one, the next `accept` sees a `confirmed` ride with a PaymentIntent, voids it on its recorded account as step `release_previous_authorization`, and then authorizes the new driver. The previous driver doesn't need to be in `declined_drivers`. See [Requeue and expiry](/engineering/payments/ride-payment-intents#requeue-and-expiry) on the payment page.

## The expiry sweep

`RideService.CancelUnmatchedRides` runs on every `Operational` tick and calls `RideOperations.ExpireUnmatched`. Each expired ride gets its own system `cancel` operation.

<Steps>
  <Step title="Find candidates">
    `ListExpiredRideOperationCandidates` returns up to 50 `confirmed` rides with no driver and `confirm_time` older than 10 minutes, oldest first. It skips rides that have a `pending` or `quarantined` operation.
  </Step>
  <Step title="Reserve under assignment locks">
    For each ride, `ReserveExpiry` opens `beginOwnedRideCommand`, which takes the same participant and ride locks as an accept and rejects a ride another operation owns. It reruns the deadline check (`RideRequestExpired`) under those locks. A ride that was accepted while the sweep ran is skipped.
  </Step>
  <Step title="Release any hold">
    The operation is a zero-fee cancellation. If the ride still has a `payment_intent_id`, the `void` step cancels it at Stripe before anything else changes.
  </Step>
  <Step title="Complete the ride">
    `CancelReservedRide` sets `status = 'complete'`, `cancel_phase = 'confirmed'`, `cancel_reason = 'automatic'`, `cancel_user = NULL`, and `complete_time`. The same transaction inserts the `no_drivers_available` ride event, enqueues `ride_request_no_drivers` for the rider with the event key `ride_operation:{operationId}:ride_request_no_drivers`, runs the revision finalizer, and finishes the operation.
  </Step>
  <Step title="Clean up">
    The operation's job removes the ride from the board provider.
  </Step>
</Steps>

The operation ID is `uuid.NewV5` of `yelo:ride:expiry:{rideId}`, so every API instance and every tick address the same row. `ExpireUnmatched` continues past a ride that fails and returns the first error.

Expired rides don't use the `no_drivers_available` status value. See [Rides implementation](/engineering/api/rides-implementation#statuses).

### Timing

Expiry is measured from `confirm_time`, which requeue resets. A ride that's requeued at minute 9 gets another 10 minutes. The sweep runs every 30 seconds on each instance, so a ride can live up to about 10.5 minutes unassigned.

Direct-request holds don't pause expiry. Queued rides never expire, however long they wait.

### Payment on expiry

Rides that were never accepted have no authorization, because authorization happens on accept or promotion, and a driver-cancel requeue voids its hold. The one ride that can expire with a hold is one that kept `payment_intent_id` through an offline unqueue or a requeue from before the journal. Expiry voids that hold and verifies the void before it completes the ride. If the void can't be verified, the ride stays `confirmed` with an unresolved operation, and no later sweep picks it up.

## Gotchas and edge cases

- **T0 is resent on every requeue.** The rematch alert's event key includes the ride's `lifecycle_revision`, so it doesn't collide with the original confirm's `ride_available:{rideId}:fleet-t0:{fleetId}` key or with an earlier requeue. A retried job reuses the key and sends nothing new. A ride without a fleet gets no rematch alert.
- **The board and the alert trail the requeue.** The ride is `confirmed` as soon as the operation finishes. It appears on the board and the drivers are alerted when the `ride_operation` job runs.
- **Unqueued rides can vanish.** Offline unqueue nulls `fleet_id`, which hides the ride from every fleet-filtered board, and keeps the old `confirm_time`, which often expires it on the next sweep. The rider gets no push when it's unqueued, only the expiry notice.
- **The cancelling driver's reason overwrites the ride's cancel fields.** `cancel_reason` and `cancel_comment` stay set on a ride that later completes normally.
- **Expiry respects ride operations.** A ride with a `pending` or `quarantined` operation isn't a candidate, and `ReserveExpiry` rejects one that gains an owner before the lock. A stuck operation therefore keeps an unmatched ride `confirmed` past 10 minutes.
- **The sweep is bounded.** Each tick handles at most 50 rides per instance.
- **A requeue voids, it never charges.** `freezeCancellation` forces the fee to 0 for a requeue, and the operation is rejected as invalid if a requeue carries a fee.
