This walkthrough follows one ride through matching. Use it to line up logs, `RideEvents` rows, and Redis state when you debug a real ride. Times are relative to confirm. Loop ticks land at arbitrary offsets, so this example assumes an `Operational` tick at 10 s past each 30-second mark.

The ride is a paid, non-discounted ride in fleet `F`, with no direct request. Default activation config. One API instance.

## Setup

- **Rider** `R` has a saved card and a requested ride from `POST /ride/v2`.
- **Driver** `D1` is online under fleet `F`, idle, with `auto_queue = false`.
- **Driver** `D2` is online under fleet `F`, idle, with `auto_queue = true` and no pause.
- **Drivers** `O1` to `O6` are offline members of `F` within 8 km.

## Confirm (t = 0)

`POST /ride/i/{id}/confirm` runs `RideService.ConfirmRide`.

| Step | Code | Touches |
| --- | --- | --- |
| Load rider and ride, pick price and fleet | `prepareConfirmRide`, `determineEffectiveRidePrice` | `Users`, `Rides`, pricing tables and caches |
| Confirm code | `generateConfirmCodeForFleet` | `Fleets.requires_confirmation_code` |
| Card checks | `validatePaymentMethod`, `processPaymentMethodParallel` | Stripe payment method read |
| Commit | `Ride.Confirm` | See below |
| Timeline | `ride_confirmed` | `RideEvents`, written asynchronously by `EventRecorder` |
| Board | `rideBoard.AddRide` | Redis `SADD rides:community:{c}`, `HSET ride:details`, `SET rides:refresh:{c} EX 10` |
| Timeline | `ride_board_added` | `RideEvents` |
| T0 | `notifyDriversAboutNewRide` | See below |

`Ride.Confirm` transaction:

1. `ListRideCommandParticipants` returns `[R]`. `R`'s `Users` row is locked, then the ride row.
2. `HasConflictingRideOperation` on `RideOperations`.
3. Rider must own the ride and it must be `requested`. `CountOtherActiveRiderRides` must be 0.
4. `ConfirmRequestedRide` sets `status = 'confirmed'`, `confirm_time`, `payment_consent_at`, `confirm_code`, `vehicle_type`, `price`, `discounted_price`, `discount_id`, `payment_method_id`, `rider_ip_address`, `rider_user_agent`, `fleet_id`, `payment_method_brand`, and `is_discounted`.
5. Finalizer: `Rides.lifecycle_revision + 1`, `Users.ride_state_revision + 1` for `R`, and a `ride_state_changed` River job when `RIDE_STATE_SNAPSHOT_ENABLED` is on.

T0:

1. `ListRideT0NotificationTargets(rideID)` joins `Rides`, `Communities`, `Fleets`, `Users`, `FleetDrivers`, `DriverApplications`, `DriverSessions`, `Vehicles`, `FleetVehicles`, and `AvailableDriverVehicles`. It returns `D1`, `D2`, and `O1` to `O6` if they all pass.
2. `notify.Emit(ride_available)` inserts a `notify_orchestrate` River job in its own transaction, with event key `ride_available:{rideId}:fleet-t0:{F}`.
3. Redis `SADD ride:notified:{rideId}` with all eight drivers and `EXPIRE 1800`.
4. `notification_dispatched` event with `tier: 0` in `RideEvents`.

Later, the orchestrator writes `Notifications`, `NotificationCohorts`, and `NotificationDeliveries`, and the send job calls Expo.

## Board polls (t = 0 to 90 s)

`D1`'s app polls `GET /ride/v2/board` every 10 seconds, and immediately after the `ride_request` push invalidates it.

| Step | Touches |
| --- | --- |
| `User.GetByID(D1)` | `Users` |
| `GetDriverSession(D1)` | `DriverSessions` |
| `GetEligibleEnrichedRideBoard` | `Rides`, `Users` (rider), `Schools`, rider rating subquery on `Rides` |
| Pickup ETAs | One Mapbox matrix call |

No writes happen.

## Tick at t = 10 s and t = 40 s

`ProcessUnmatchedRides`:

| Step | Touches |
| --- | --- |
| `ListUnmatchedRidesForActivation` | `Rides` |
| `loadConfig` | Redis `GET activation_config:{c}`. On a miss, `ActivationConfigs` then `SET ... EX 300` |
| `determineTierIdx` | Redis `HGET ride:notify:{rideId} tier`, which returns nothing, so tier 0 |
| Tier check | 10 s and 40 s are both under 45 s, so nothing fires |
| Auto-queue pass | Skipped, because the ride is under 2 minutes old |

`CancelUnmatchedRides` and `PurgeOfflineDrivers` run concurrently on the same tick. They don't select this ride.

## Tick at t = 70 s: tier 1

| Step | Touches |
| --- | --- |
| `determineTierIdx` | `HGET ride:notify:{rideId}` is empty, 70 s is at least 45 s, so tier 1 |
| `buildExcludeSet` | `SMEMBERS ride:notified:{rideId}`, which returns the eight T0 drivers |
| Warm pool | `ZRANGEBYSCORE community:warm:{c}`, then `ZREMRANGEBYSCORE` to trim. Empty |
| `rideFleetIsCommunityPrimary` | `Communities.primary_fleet_id` |
| `ListNearbyInactiveDrivers` | `Users`, `DriverApplications`, `Vehicles`, `FleetDrivers` |
| Filter | Drops `O1` to `O6`, which are in the exclude set. Other offline drivers in range pass |
| Cooldown | `SET driver:activation_cd:{id} 1 NX EX 900` per passing driver |
| Names | `GetNamesByIDs` on `Users` |
| Timeline | `activation_tier_reached` with `tier: 1` |
| Push | River job, event key `unclaimed_ride:{rideId}:tier:1:recipients:{hash}` |
| Bookkeeping | `SADD ride:notified:{rideId}`, then `HSET ride:notify:{rideId} tier 1 ts {now}` and `EXPIRE 1200` |

If every nearby offline driver was a T0 recipient, the tier finds nobody. It still writes `tier = 1` and records the event with `drivers_notified: 0`.

    | Verify hold | `InspectRideAuthorization` | Stripe read |
    | Finalize | `RidePreparationCommands.Finalize` | See below |
    | Board | `ReconcileRideOperation`, from the `ride_operation` job | `SREM rides:community:{c}`, `HDEL ride:details`, `SET rides:refresh:{c} EX 10` |
    | Queue summary | `ReconcileRideOperation`, same job | `ListDriverQueuedRides` is empty, so `DEL driver:queue_summary:{D1}` and `DEL driver:queue_ride_etas:{D1}` |
    | Effect receipt | `CompleteRideOperationEffects` | `RideOperationEffectReceipts` |

    Reservation transaction:

    1. Participants: `R`, `D1`, and riders of any rides `D1` has in progress. Lock `Users` rows in UUID order, rediscover, lock the ride.
    2. `HasConflictingRideOperation`.
    3. `status` must be `confirmed` with no driver, at the revision and generation the command read.
    4. `GetRideAcceptanceSession` must return the session start the command carries. `GetRideCommandDriverAvailability(D1)` for `is_online_driver`. `GetDriverSessionOwnership` needs exactly one open session matching `D1`'s vehicle and fleet.
    5. `CanAcceptDirectRide` passes because there's no hold.
    6. `GetRideOperationPaymentDecision` checks the fleet. `GetRideAcceptingDriver` returns `queue_length = 0` and the drive count.
    7. `AssignAcceptedRideToDriver` sets `status = 'driver_en_route'`, `driver_id`, `driver_vehicle_id`, `fleet_id`, `match_time`, `driver_drive_count`, and clears `potential_driver` and `offer_time`. The pickup fields are empty until finalization.
    8. `freezeRidePreparation` reads the fare, the rider's customer and payment method, the consent fields, and the connected account (fleet account if custom payouts, else `D1`'s) into the operation's inputs.
    9. Finalizer: `lifecycle_revision + 1`, `assignment_generation + 1`, and `ride_state_revision + 1` for `R` and `D1`.
    10. `InsertRideOperation` and a `ride_operation` River job on `ride_operations`.

    Finalization transaction, after the Stripe steps:

    1. The same locks, then `LockRideOperation`.
    2. `AddRidePaymentIntent` writes `payment_intent_id`, `payment_intent_client_secret`, `pre_auth_amount`, `cloned_payment_method_id`, and `stripe_merchant_id`. `UpdateRidePickupRoute` writes the pickup fields.
    3. Finalizer: `lifecycle_revision + 1` again.
    4. `FinishRideOperation` sets the operation to `succeeded`, and `ride_accepted` is inserted into `RideEvents` with the operation ID.
    5. A `notify_orchestrate` River job for `ride_confirmed` to `R`, with event key `ride_operation:{operationId}:ride_confirmed`.

    Redis keys left behind: `ride:notified:{rideId}` expires 30 minutes after the last add, `ride:notify:{rideId}` 20 minutes after tier 1. Cooldowns on tier 1 drivers last 15 minutes and block them from other rides.

  <Tab title="Nobody accepts, D2 auto-queued at t = 130 s">
    The tick at 100 s does nothing new. The tick at 130 s fires tier 2 first, the same way as tier 1 with a 13 km radius, target 10, and a warm age of 60. Then the auto-queue pass runs, because the ride is at least 120 s old.

    | Step | Code | Touches |
    | --- | --- | --- |
    | Flag | `HasAutoQueueAttempted` | `EXISTS ride:aq_attempted:{rideId}` |
    | Candidates | `ListAutoQueueEligibleDrivers` | `Users`, `DriverApplications`, `Vehicles`, `DriverSessions`. Returns `D2` |
    | Community limits | `GetCommunityAutoQueueSettings` | `Communities` |
    | Queue load | `GetQueueSummary(D2)` | `HMGET driver:queue_summary:{D2}`. Missing, so an empty queue |
    | Deadhead | `GetDistances` | Mapbox matrix, one origin |
    | Score | `scoreAutoQueueCandidates` | One candidate wins with score 0 |
    | Session | `GetByID(D2)`, `GetDriverSession(D2)` | `Users`, `DriverSessions` |
    | Assign | `AutoAssignRide` | See below |

    `AutoAssignRide` calls `AutoAssignLegacy`, which submits the same `accept` operation as a manual accept with `Automatic` set and the scoring decision attached.

    1. Reservation runs the manual-accept transaction with three differences. It also requires `accepts_auto_queue`, it passes `uuid.Nil` to `CanAcceptDirectRide`, and `MarkRideAutomaticallyAssigned` sets `auto_queued = true`. `D2` has no other ride, so the status is `driver_en_route`. The operation's actor is `system`.
    2. The reservation inserts a `ride_auto_queued` event with `candidate_count`, `deadhead_minutes`, `final_score`, `queue_load`, and `elapsed_since_confirm_ms`.
    3. The same clone, create, confirm, route, and verify steps run.
    4. Finalization writes the payment and pickup fields, inserts `ride_accepted` with `automatic: true`, and enqueues two pushes: `ride_confirmed` to `R` and `ride_auto_queued` to `D2`, each keyed by the operation ID.
    5. The operation's job removes the ride from the board and refreshes `D2`'s queue summary.

    If `D2` already had a ride, step 1 would write `status = 'queued'` and steps 3 and 4 would skip payment and routing. The ride is authorized later by its `promotion` operation. See [Queue promotion and recovery](/engineering/matching/queue-promotion#the-promotion-operation).

## If nobody ever matches

| Time | Event |
| --- | --- |
| 300 s or later | Tier 3, 16 km, target 15 |
| 480 s or later | Tier 4, 16 km, target 20, ignores the notified set but not cooldowns |
| 600 s or later | Next `CancelUnmatchedRides` tick expires the ride through a system `cancel` operation: `status = 'complete'`, `cancel_reason = 'automatic'`, `cancel_phase = 'confirmed'`, `no_drivers_available` event, and a `ride_request_no_drivers` push with key `ride_operation:{operationId}:ride_request_no_drivers`, all in one transaction. The operation's job then removes the ride from the board |

## Gotchas and edge cases

- **Some timeline events are asynchronous.** `EventRecorder` buffers up to 500 events and drops one after 100 ms of backpressure, so the events it writes (`ride_confirmed`, `ride_board_added`, tier and notification events) can be missing or slightly out of order. The events a ride operation writes (`ride_accepted`, `ride_auto_queued`, `queue_promoted`, `ride_completed`, `ride_canceled`, `auto_requeued`, `no_drivers_available`, `tip_captured`, `tip_window_expired`) are inserted in the operation's own transaction and can't be dropped.
- **Tick phase matters.** The same ride can see tier 1 anywhere from 45 to 75 seconds after confirm, and auto-queue anywhere from 120 to 150 seconds, depending on when the loop ticks relative to confirm.
- **Every accept assigns before it authorizes.** Manual accept and auto-queue both commit the assignment at reservation and create the hold afterwards. If the card is declined, the ride is canceled with `cancel_reason = 'Payment Failed'` and the rider gets `ride_payment_failed`. For a busy driver, the ride waits `queued` and the card is only tried at promotion.
- **The board trails the accept.** The ride leaves the Redis board when the operation's `ride_operation` job runs, shortly after the accept returns. A second driver who taps in that window gets "Ride Unavailable" from the reservation.
- **An assigned ride briefly has no pickup route.** Between reservation and finalization, `pickup_distance`, `pickup_duration`, and `pickup_route` are 0, 0, and empty.
- **Every tier writes Redis even with zero recipients.** An empty tier still consumes its slot in `ride:notify:{rideId}`, so a driver who comes into range later is only reached by the next tier or the pending-ride push.
