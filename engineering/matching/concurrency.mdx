Matching is contended by design. Drivers accept from the board, auto-queue assigns in the background on every instance, riders cancel, and sweeps expire. None of this is coordinated in Go. Every decision that matters is rechecked in a Postgres transaction under row locks.

This page goes deeper than [Rides implementation](/engineering/api/rides-implementation#locking-and-command-transactions).

## The lock hierarchy

| Level | Mechanism | Scope | Used by |
| --- | --- | --- | --- |
| 1 | `SELECT ... FOR UPDATE` on `Users` rows, sorted by UUID string | Every participant of the command | Every ride command, offline purge, expiry sweep |
| 2 | `SELECT ... FOR UPDATE` on the `Rides` row | The target ride | Every ride command with a ride ID |
| 3 | `pg_advisory_lock(key)` on a dedicated connection | The ride being accepted | `acceptFinancialRide`, on manual accept |
| 3 | A `pending` or `quarantined` row in `RideOperations` | The ride, across transactions, for as long as a financial command is unresolved | Every ride operation |
| 4 | Redis `SET NX` | Activation cooldowns, rescue alerts | Activation loop |

Levels 1 and 2 are always taken in that order. The advisory lock is taken before any row locks, outside the transaction. Operation ownership isn't a database lock. It's a row that every command checks after taking levels 1 and 2. See [Operation ownership](#operation-ownership).

## Participant discovery

`beginOwnedRideCommand` in `internal/data/repository/ride_command.go`:

```go
for range 4 {
	tx := BeginTx()
	state, retry, lockErr := lockRideCommand(ctx, tx, rideID, driverID)
	if lockErr == nil && !retry {
		// reject if another durable ride operation owns the ride
		return tx, state, nil
	}
	rollback(tx)
}
return rideCommandConflict()
```

`lockRideCommand` does this inside the transaction:

1. `ListRideCommandParticipants(rideID, driverID)` finds everyone the command could affect: the ride's rider and driver, the explicit driver argument, and the riders and drivers of every ride in those drivers' `queued`, `driver_en_route`, `driver_waiting`, or `in_progress` states.
2. `lockRideParticipants` sorts the IDs as strings, deduplicates them, and locks each `Users` row.
3. It runs the discovery query again. If a new participant appeared, it signals a retry.
4. `LockRideCommandState` locks the ride row and reads `rider_id`, `driver_id`, `status`, `lifecycle_revision`, and `assignment_generation`. If the ride's rider or driver isn't in the locked set, it signals a retry.

Locks are never appended out of order. A participant set that changed means rollback and start over. After 4 attempts, the command fails with a conflict.

The error every lock and state check returns:

```go
errors.NewError("ride state changed", errors.ErrorTypeInput, "Ride Unavailable",
	"This ride has changed. Refresh and try again.")
```

That's a 400.

### Why queue riders are locked

Promoting a queued ride changes another rider's ride. The revision finalizer also bumps `ride_state_revision` on every rider in the affected drivers' queues. Locking them up front means the finalizer's `UPDATE "Users"` never waits on a lock outside the sorted order.

## Operation ownership

A command that moves money can't hold row locks while it talks to Stripe or Mapbox. It reserves the ride instead. `beginOwnedRideCommand` runs `HasConflictingRideOperation` after it locks the ride, and rejects the command with "Ride Unavailable" when another operation on the ride is `pending` or `quarantined`. The unique partial index `ride_operations_one_unresolved` enforces the same rule in the database.

| Phase | Locks held | Revision check |
| --- | --- | --- |
| Reserve | Levels 1 and 2 | The ride must be at the `lifecycle_revision` and `assignment_generation` the command read. The operation row stores the pair it expects to see at finalization |
| Execute | None. Stripe, Mapbox, and Google calls run here | — |
| Finalize | Levels 1 and 2, then the operation row | `matchesRideCommandRevision` requires the ride to still be at the stored pair |

Between reservation and finalization, no other command can commit a change to the ride, because each one fails the ownership check. The finalizer's revision check is a second line of defense. `accept` and idle promotion change the ride during reservation, so their stored revision is the one after that change.

See [Reserve, then execute](/engineering/payments/ride-operation-journal#reserve-then-execute).

## The revision finalizer

`finalizeOwnedRideCommand` in `ride_revision.go` runs last in every lifecycle transaction. For each changed ride:

```sql
UPDATE "Rides" SET lifecycle_revision=lifecycle_revision+1,
 assignment_generation=assignment_generation+CASE WHEN
 (CASE WHEN status IN ('queued','driver_en_route','driver_waiting','in_progress') THEN driver_id ELSE NULL END)
 IS DISTINCT FROM sqlc.narg(previous_assignment)::uuid THEN 1 ELSE 0 END
WHERE id=sqlc.arg(ride_id)::uuid RETURNING rider_id,driver_id;
```

`assignment_generation` counts changes of the effective assignee:

| Command | Previous assignee | New assignee | Generation |
| --- | --- | --- | --- |
| Confirm | None | None | Unchanged |
| Accept or auto-queue | None | Driver | +1 |
| Promotion | Driver | Same driver | Unchanged |
| Requeue or unqueue | Driver | None | +1 |
| Complete | Driver | None, because `pending_rider_rating` isn't an assigned status | +1 |
| Expiry | None | None | Unchanged |

Then it collects the rider, the current driver, the previous assignee, and every rider queued behind any of those drivers. It increments each one's `Users.ride_state_revision` in sorted order. When `RIDE_STATE_SNAPSHOT_ENABLED` is true, it enqueues a `ride_state_changed` push per user with event key `ride_state:{userId}:{revision}`, in the same transaction.

The finalizer also re-runs `HasConflictingRideOperation` over every changed ride, excluding the operation that owns the command. A transaction that changes a second ride, such as a completion that promotes the next queued ride, fails if that second ride has an unresolved operation of its own.

## The advisory lock

`sqlRideRepository.AcquireLock` in `ride.go`:

```go
lockKey := int64(binary.BigEndian.Uint64(b[:8]))
conn, err := r.postgresDb.Acquire(ctx)
queries.AcquireRideAdvisoryLock(ctx, lockKey)           // SELECT pg_advisory_lock($1)
unlockCtx := context.WithoutCancel(ctx)
release := func() {
	defer conn.Release()
	queries.ReleaseRideAdvisoryLock(unlockCtx, lockKey) // SELECT pg_advisory_unlock($1)
}
```

It has one user. `acceptFinancialRide` takes the lock on a manual accept, before it looks up or creates the `accept` operation, and holds it until the command returns. That covers the reservation, the Stripe steps, and the pickup route. A duplicate accept from the same driver waits for the first one to finish and then replays its operation.

It isn't a correctness lock. Reservation rechecks everything under row locks, and operation ownership stops a second hold. Auto-queue assignment and idle recovery don't take it.

It holds a pool connection for the whole accept, including network calls to Mapbox and Stripe.

## Race scenarios

<AccordionGroup>
  <Accordion title="Two drivers tap accept on the same ride">
    Both call `AcquireLock` on the ride's advisory lock:

    1. The first accept takes the lock, reserves the assignment, authorizes payment, and finalizes.
    2. The second waits on the lock. Once it gets the lock, its reservation finds a ride that is no longer `confirmed` with no driver, and fails with "Ride Unavailable".

    The loser is rejected at reservation, before any Stripe call, so no second intent is created on the loser's account.
  </Accordion>
  <Accordion title="Driver retries an accept">
    A driver's app can send the same accept twice, for example after a lost response or a double tap. The second request waits on the ride's advisory lock until the first finishes. `AcceptLegacy` then finds the driver's `accept` operation for the current assignment and resubmits the same command ID with the original session, vehicle, and fleet. Reservation returns the stored row, and the executor replays the stored outcome. It doesn't create another payment intent or change the assignment. The rider's push is keyed by the operation ID, so it isn't sent again.

    If the first request died after reserving, the retry continues the same operation from its last committed step.
  </Accordion>
  <Accordion title="Manual accept races auto-queue">
    Both reserve an `accept` operation. Auto-queue doesn't take the advisory lock, so the ride row lock serializes them. The first to commit wins. If auto-queue loses, `AutoAssignRide` returns the conflict, and `assignWinner` logs "Auto-queue assign failed, ride may have been claimed" without setting the attempted flag. The ride is no longer unmatched, so it isn't retried. If the driver loses, they see "Ride Unavailable".
  </Accordion>
  <Accordion title="Rider cancels while a driver accepts">
    A cancellation is bound to a quote, and the quote stores the `lifecycle_revision` and `assignment_generation` it was issued at.

    - Accept reserves first: the cancel is rejected while the `accept` operation is unresolved. After it finishes, a quote issued before the accept no longer matches the ride's revision. For a ride that now has a hold, the rider gets "Review cancellation fee" and must reopen cancellation to price it against the assigned ride.
    - Cancel reserves first: the accept's reservation is rejected with "Ride Unavailable" while the `cancel` operation is unresolved, and afterwards because the ride is `complete`. The accept never reached Stripe, so no intent is left behind.
  </Accordion>
  <Accordion title="Accept races the expiry sweep">
    Expiry reserves a system `cancel` operation through `beginOwnedRideCommand`, which locks the same rider and ride that an accept locks. `ReserveExpiry` rechecks `status = 'confirmed'`, no driver, and the deadline under those locks. Whichever reserves first wins. If accept wins, the recheck fails and the sweep skips the ride. If the sweep wins, the accept's reservation is rejected.
  </Accordion>
  <Accordion title="Completion races idle recovery">
    Driver completes ride A with ride B queued. At the same moment, the 3-minute loop runs `RecoverIdleQueue` for the same driver.

    - The `complete` finalizer runs `PromoteNextQueuedRide` and reserves B's `promotion` operation in the transaction that ends A. There's no committed state where A is finished and B is still `queued` with a free active slot.
    - Recovery stops when it reads an active ride, which is A before that commit and B after it.
    - If recovery does reach `ReserveIdle` for B, it derives the same operation ID from the ride and its `assignment_generation`, finds the existing `promotion`, and continues it.
  </Accordion>
  <Accordion title="Two instances recover the same driver">
    Both call `PromoteIdle` for the same queue head and derive the same operation ID. One reserves it. The other finds the row, either before or after taking the ride locks, and executes the same operation. Each step's request and receipt are in the journal, so the second executor replays what the first one finished.
  </Accordion>
  <Accordion title="Driver switches vehicle during an accept">
    The service reads the session's vehicle and fleet before locking. `validateRideAssignmentDriver` rereads under the driver's `Users` lock and requires exactly one open session matching those IDs. Session rotation takes the same driver lock, so either the rotation or the accept sees the other's result.
  </Accordion>
  <Accordion title="Two instances fire the same activation tier">
    Both read `ride:notify:{rideId}` as tier 0 and pick tier 1. Cooldown `SETNX` gives each instance a disjoint set of drivers. Their event keys differ because they hash different recipients, so both pushes go out. Tier 1 reaches up to twice its target. Both then write tier 1.
  </Accordion>
  <Accordion title="Decline retried after the ride was matched">
    `DeclineRide` returns success if the driver is already in `declined_drivers`, before checking status. A retry after a lost response succeeds even if another driver has since accepted.
  </Accordion>
</AccordionGroup>

## Gotchas and edge cases

- **Service-level reads are advisory.** `AcceptLegacy` reads the ride state and the driver's open session without locks to build the command. Reservation repeats every check under row locks.
- **External calls happen outside transactions.** Mapbox and Stripe calls never run while row locks are held. On a manual accept they do run while the advisory lock is held.
- **Four retries isn't much under churn.** A driver whose queue changes on every attempt, for example during a burst of auto-queue assignments, can see "This ride has changed" without any real conflict on the ride itself.
- **A stuck operation is a stuck ride.** Ownership has no timeout. A `quarantined` operation, or a `pending` one whose job keeps failing, rejects every other command on the ride. See [Quarantine](/engineering/payments/ride-operation-journal#quarantine).
- **A declined card on accept cancels the ride.** The assignment is committed before authorization. A declined authorization finishes the `accept` operation as `failed` and cancels the ride with `cancel_reason = 'Payment Failed'`. It doesn't go back on the board.
- **Unlock failures leak the advisory lock.** The connection returns to the pool still holding it. See [Queue promotion and recovery](/engineering/matching/queue-promotion#idle-recovery).
- **Redis isn't transactional with Postgres.** Notified sets, tiers, and flags are written after commit, and a crash between commit and those writes leaves Redis behind. Board and queue-summary writes that follow a ride operation are retried by its job until `RideOperationEffectReceipts` has a row. Every Redis-derived decision is revalidated in Postgres before it assigns anything.
