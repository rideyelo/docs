This is the reference for every `TemplateCode` in `yelo-api/internal/notify/codes.go`. Copy and settings below are the **seed values** in `internal/notify/seed/templates.go`. The seeder never overwrites an existing row, so production copy may differ if an admin edited it. Check the dashboard (**Notifications** > **Templates**) for live copy.

For how a code moves from emit to device, see [Push send pipeline](/engineering/notifications/send-pipeline). For how the app reacts, see [Mobile push handling](/engineering/notifications/mobile-push-handling).

## How to read this page

- **Trigger** is the function that calls `notify.Emit`, directly or through `NotificationService` in `internal/service/notifications/notification.go`.
- **Deep link** is the template's `deeplink`, rendered with the variables and sent as `data.url`.
- **`data.type`** is the template's `client_data_type` if set, otherwise the code. Caller `WithData` keys override it.
- **Fresh** means the orchestrate job is canceled after 15 minutes. See [Freshness](/engineering/notifications/send-pipeline#freshness).
- **App** summarizes `invalidateForPush` in `yelo-frontend/lib/notifications/pushInvalidation.ts`. "Ride refresh" means the ride-status invalidation group. "None" means the push only shows a banner and navigates on tap.

Every push also carries `notification_id`, `notification_delivery_id`, `cohort_id`, and `variant_id`, added by the send worker. Ride-bound pushes carry `ride_id`.

### Rider gating

`ride_confirmed` (from `AcceptRide`), `driver_arrived`, `ride_completed`, and `ride_canceled_by_driver` go through `RideService.notifyRiderOfRideUpdate`:

- It skips the emit if the rider has no token or `allow_notifications` is false.
- It checks the legacy `RideNotifications` table (`IsNotified`) for this ride and type and skips if one exists.
- It writes the `RideNotifications` row only after the emit succeeds.

This is a second, permanent dedupe on top of the event key. The promotion and auto-queue paths for `ride_confirmed` skip this gate and only check that the rider has a token.

### T0 fleet targets

`ListRideT0NotificationTargets` (`internal/data/repository/queries/community.sql`) returns drivers who:

- Belong to the ride's active fleet and community, with an active `FleetDrivers` row and an active driver application.
- Drive a vehicle of the ride's `vehicle_type` with enough seats and `application_status = complete`. Online drivers use their session vehicle, offline drivers their default vehicle.
- Are online under the same fleet, or offline.
- Have a token, allow notifications, are not deleted, banned, or locked, and have not declined the ride.
- Have payout readiness: `stripe_status = complete`, or a complete fleet merchant with custom payouts.
- Have fewer than `matching.MaxQueueLength` open rides.
- For the fleet named `Yelo`, carry a `Founding Driver`, `founding driver`, or `founding` tag.

## Adding a code

<Steps>
  <Step title="Declare the code and variables">
    Add a `TemplateCode` constant and a `Vars` struct with `notify:"name[,required]"` tags in `codes.go`, and register it in `Registry`.
  </Step>
  <Step title="Seed the template">
    Add a `TemplateSeed` in `seed/templates.go`. CI checks that every registered code has a seed. The loader runs on every boot and fails the instance if seeding fails, so a new code ships with its row.
  </Step>
  <Step title="Classify it">
    Add the code to `orchestrationFreshnessForCode` and `bypassesCooldowns`. Both switches are exhaustive under lint, so a missing case fails the build.
  </Step>
  <Step title="Handle it in the app">
    If the push should refresh cached data, add its `data.type` to `invalidateForPush`. Otherwise the app only shows it.
  </Step>
</Steps>

## Gotchas and edge cases

<AccordionGroup>
  <Accordion title="Renew reminders lose cohorts to the 5-minute bucket">
    `PurgeOfflineDrivers` runs every 30 seconds and each run targets a different 30-second slice of drivers. The event key is `driver_renew_online:{community}:{unix/300}`, so every run after the first in a 5-minute bucket collides and is dropped as `deduped`. In practice only the first cohort in each 5-minute window gets the reminder.
  </Accordion>
  <Accordion title="Fleet T0 is skipped after a requeue">
    `notifyDriversAboutNewRide` uses `ride_available:{ride}:fleet-t0:{fleet}`. When a driver cancels and the ride is requeued, it is called again with the same key, so the fleet never gets a second T0 alert. `resumeExpiredDirectRide` uses the same key, so a direct offer that already triggered T0 cannot trigger it again either.
  </Accordion>
  <Accordion title="Drivers do not see the ride on the board from unclaimed_ride">
    Activation pushes use `data.type` `unclaimed_ride` and `unclaimed_ride_fleet`, which the app does not map to a board refresh. Only `ride_available` (sent as `ride_request`) refreshes the board. Drivers who tap an activation push land on `/drive` and see the ride on the next 10-second board poll.
  </Accordion>
  <Accordion title="Deep links that do not resolve in the app">
    `driver_application_approved` points at `/driver-signup/1-application-status`, which has no route. The payout codes point at `yelo://drive/earnings`, but earnings lives at `driver-earnings/`. `ride_completed` points at `ride?rate={{ride_id}}`, but `app/(app)/ride/index.tsx` redirects to the map and nothing reads `rate`.
  </Accordion>
  <Accordion title="Rider-cancel notification is marked sent even when it fails">
    `handleRiderCancellation` writes the `RideNotifications` row even when the emit returns an error, unlike `notifyRiderOfRideUpdate`. A transient enqueue failure permanently suppresses `ride_canceled_by_rider` for that ride.
  </Accordion>
  <Accordion title="Activation marks drivers as notified even when the push is suppressed">
    `activateForConfigTier` adds drivers to the Redis notified set once the emit is enqueued. If the orchestrator then suppresses a driver for `user_cooldown` or a missing token, activation still treats them as pinged and excludes them from later tiers that do not re-ping.
  </Accordion>
  <Accordion title="Copy edits on the server do not change data.type">
    Changing `client_data_type` in the dashboard changes what the app sees. Setting `ride_available` to anything other than `ride_request` stops driver boards from refreshing.
  </Accordion>
</AccordionGroup>
