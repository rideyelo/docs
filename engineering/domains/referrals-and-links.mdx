Referrals connect three systems: a code on `Users.referral_code`, a Dub short link on `join.yelo.link`, and a `Referrals` row written at sign-up. Rewards are computed at read time from `ReferralRewards` and `ReferralPayouts`. Nothing is paid out automatically.

This page covers the API side. For the product view, see [Growth features](/concepts/growth-features). For how a code is bound to an Auth v3 sign-in, see [Auth v3 transactions](/engineering/identity/auth-v3-transactions). Fleet join links also use Dub; see [Joins and invitations](/engineering/fleets/joins-and-invitations).

## Referral codes

`GenerateReferralCode` in `internal/utilities/referral/generate.go` builds `INITIALS-XXXXX`:

- First initial: first byte of the trimmed first name, uppercased. Empty becomes `X`.
- Last initial: same rule for the last name.
- Suffix: 5 characters drawn with `crypto/rand` from `23456789ABCDEFGHJKMNPQRSTUVWXYZ` (31 characters, no `0`, `1`, `I`, `L`, `O`).

That gives 31^5 = 28,629,151 suffixes per initials pair. A user named "Sam Lee" gets something like `SL-7QK2M`.

Three writers assign codes. Each checks for collisions differently.

| Writer | When | Collision check | Attempts |
| --- | --- | --- | --- |
| `AuthV2Service.generateReferralCode` (`service/authv2/profile.go`) | First Auth v2 profile setup | `GetAuthUserByReferralCode` returns not found | 10, then server error |
| `CompleteAuthV3Profile` (`data/repository/authv3.go`) | Auth v3 profile completion, only when `referral_code` is blank | `pg_advisory_xact_lock(hashtextextended(code, 0))` then `AuthV3ReferralCodeExistsForOtherUser` (case-insensitive) | Collision returns `ErrorTypeDuplicate`; the service retry loop retries |
| `ReferralService.GetOrCreateShareLink` | `GET /referral/link` for a code without a hyphen | `GetAuthUserByReferralCode` returns not found | 10, then 400 "Failed to generate unique code" |

Auth v2 reuses an existing code on re-verify and only calls `CreateDubLinkAsync` when the user had no code before.

## Share links

A user's Dub link is a projection of three inputs: their referral code, their profile (name and photo, baked into the signed card), and the current link configuration (`INVITE_LANDING_BASE_URL`, `OG_IMAGE_BASE_URL`, and `shareLinkVersion`). The API records what Dub holds in `share_link_created_at` and `share_link_fingerprint`, so drift is detected and repaired automatically instead of by a manual backfill.

<Steps>
  <Step title="Build the link">
    `GetOrCreateShareLink` loads the user and builds `https://join.yelo.link/<code>?v=4`. `shareLinkVersion` is `"4"`. Bump it to force iMessage to re-scrape previews. Because it is part of the config version, a bump also makes the sweep rewrite every existing link with the current card.
  </Step>
  <Step title="Migrate legacy codes">
    If the code has no hyphen, `migrateLegacyCode` generates a new code, upserts the Dub link, and runs `UpdateReferralCode` to set `referral_code` and keep the old code in `old_referral_code`. It then marks the link synced.
  </Step>
  <Step title="Sync the link">
    Otherwise `syncShareLink` builds the Dub request and computes its fingerprint. If the stored `share_link_fingerprint` matches, nothing is sent to Dub. If not, `createDubLink` calls `DubProvider.UpsertLink` and `MarkUserShareLinkSynced` stores the new fingerprint and sets `share_link_created_at` (first time only).
  </Step>
  <Step title="Fall back when Dub fails">
    If the sync fails and the user already has a link (`share_link_created_at` set), the handler logs a warning and still returns the existing link. If the user has no link yet, the request returns 500.
  </Step>
</Steps>

### Fingerprints

The fingerprint has the form `<config version>:<request hash>`.

- **Config version**: the first 4 bytes (8 hex characters) of SHA-256 over `join.yelo.link`, `INVITE_LANDING_BASE_URL`, `OG_IMAGE_BASE_URL`, and `shareLinkVersion`.
- **Request hash**: the first 8 bytes (16 hex characters) of SHA-256 over the request's `Domain`, `Key`, `URL`, `Title`, `Description`, and `Image`.

A name or photo change alters the request hash. A configuration change alters the config version prefix, which makes every existing link stale at once.

`buildDubLinkRequest` sends:

| Field | Value |
| --- | --- |
| `Domain` | `join.yelo.link` (`dubBaseDomain`) |
| `Key` | The referral code |
| `ExternalID` | The user ID |
| `URL` | `INVITE_LANDING_BASE_URL + "/" + code`. `INVITE_LANDING_BASE_URL` defaults to `https://joinyelo.com/i`, the first-party landing page. |
| `FolderID` | `DUB_SYSTEM_FOLDER_ID` |
| `Title` | `Join <first name> on Yelo` |
| `Description` | `<first name> invited you to Yelo — tap to get the app and ride together.` |
| `Image` | Signed OG card URL (below) |
| `TagNames` | `system`, `referral` |
| `TrackConversion` | `true` |
| `Proxy` | `true` |

The Dub client (`internal/data/dub/dub.go`) builds a new SDK client per call from `DUB_API_KEY`. Empty fields are omitted from the upsert body.

Dub's upsert matches an existing link by destination URL, not by key. Changing the destination of an existing key (for example, after `INVITE_LANDING_BASE_URL` changes) makes Dub return a duplicate-key conflict. On that conflict, `UpsertLink` looks the link up by domain and key with `Links.Get` and rewrites it in place with `Links.Update`, sending the URL, title, description, image, `TrackConversion`, and `Proxy`.

### Background creation and refresh

| Function | Trigger | Context | Retries | On success |
| --- | --- | --- | --- | --- |
| `CreateDubLinkAsync` | First Auth v2 profile setup | Detached, 30 s | `retry.NewNetworkRetrier`: 5 attempts, 200 ms base delay, 10 s max, full jitter | `SyncShareLink` with create-if-missing |
| `RefreshShareCardAsync` | `UserService.UpdateName` and `UpdateProfilePicture` (after the thumbnail is saved) | `context.Background` with 30 s timeout | None; the sweep retries | `MarkUserShareLinkStale`, then `SyncShareLink` without create |
| `share_link_sweep` (River) | Every minute | 50 s job timeout | Next run | `SyncStaleShareLinks` |

Every writer goes through the same sync path, which is a no-op when Dub already matches. `RefreshShareCardAsync` first clears `share_link_fingerprint`, so if the rewrite fails or the process dies, the sweep still repairs the card. Users with no link yet are left alone. Their link is created from the current profile on the first `GET /referral/link`.

Auth v3 profile completion doesn't call `CreateDubLinkAsync`. Those users get their Dub link lazily on the first `GET /referral/link`.

### Self-healing sweep

The `share_link_sweep` River job runs once a minute (`RunOnStart: true`, unique per 50 s period). Each run:

1. Lists up to 40 users in random order whose link exists (`share_link_created_at IS NOT NULL`), who aren't deleted, have a non-blank code, and whose fingerprint is `NULL` or doesn't start with the current config version.
2. Calls `SyncShareLink` for each. A failure logs a warning and the next user continues. Random order stops one permanently failing user from starving the batch.
3. Counts the remaining stale links.

At 40 links per minute, the sweep rewrites a few thousand links an hour. A normal run finds nothing to do. The job is skipped when the Dub client is not configured.

To repoint every existing personal invite link, change `INVITE_LANDING_BASE_URL` (or `OG_IMAGE_BASE_URL`) and deploy. The config version changes, so the sweep rewrites each link once. The old `cmd/backfill-referral-links` command was removed.

### Signed OG card

`ogcard.InviteCardURL` (`internal/utilities/ogcard/url.go`) builds `OG_IMAGE_BASE_URL/og/invite?<params>&sig=<hmac>`. The signed params are:

| Param | Value |
| --- | --- |
| `n` | First name |
| `l` | Last name, omitted when blank |
| `c` | Deterministic avatar color from the user ID |
| `p` | Photo URL, omitted when blank |
| `v` | Card design version (`inviteCardDesign`, currently `"2"`) |

The worker ignores `v`, but it is part of the signed URL. Card responses are cached as immutable, so bump `inviteCardDesign` after deploying a new invite template to the `og` worker. Otherwise every preview keeps serving the old image. The new image URL changes each link's request hash, so the next sync rewrites it.

```text
https://<og-worker>/og/invite?c=%23C05A5A&n=Alex&v=2&sig=<hmac>
```

| Param | Source | Included when |
| --- | --- | --- |
| `n` | First name | Always |
| `c` | `HexColor(DeterministicColor(user_id))` | Always |
| `l` | Last name | Non-empty |
| `p` | `PhotoThumbnailUrl` | Non-empty |

The signature is HMAC-SHA256 with `OG_SIGNING_SECRET` over a canonical string, truncated to 32 hex characters (`SigLength`). The canonical string sorts keys, skips `sig`, and length-prefixes each key and decoded value in bytes, for example `1:c=6:5AC0771:n=3:Sam`. Length prefixes stop a crafted first name from forging a `p` parameter. `yelo-web/workers/og/src/sign.ts` must produce identical strings.

After each upsert, `warmOGCardAsync` sends a `GET` to the image URL on a detached 15-second context. A non-200 only logs "OG card warm failed".

## Applying a referral

| Path | Function | Lookup | Self-referral | Failure behavior | Side effects |
| --- | --- | --- | --- | --- | --- |
| Auth v3 profile completion | `CompleteAuthV3Profile` calls `applyAuthV3Referral` | `GetAuthV3ReferrerIDByCode`: `upper(btrim(referral_code))`, excludes deleted and banned users | 400 "referral code is invalid" | Fails the whole profile transaction | Mutual friendship (`source = referral`) in the same transaction as the `Referrals` row |
| Auth v3 ambient referral | `CompleteAuthV3Profile` calls `applyAuthV3AmbientReferral` when the user presented no code | `GetAuthV3AmbientReferralCode`: most recent code on the user's claimed anonymous touches (touches made inside an auth transaction are excluded) | Dropped | Invalid, stale, or conflicting codes are dropped. Only a server error fails the profile. | Same as above |
| Auth v2 profile setup | `AuthV2Service.applyReferralCode` | `GetAuthUserByReferralCode`: exact match on `referral_code` **or** `old_referral_code` | "Cannot refer yourself" | Logged and ignored; setup continues | Mutual friendship (`source = referral`), `acquisition_source` promoted from `app_organic` to `app_referral` |
| Auth v2 community signup | `applyReferralCode` from `service/authv2/community.go` | Same as above | Same | Logged and ignored | Same, plus `fireDubTrackLead` |

Both inserts use `ON CONFLICT (referee_id) DO UPDATE SET referrer_id = "Referrals".referrer_id RETURNING referrer_id`. The existing referrer is kept. If the returned ID differs, the repository returns `ErrorTypeIdentityConflict`.

In Auth v3, a code captured on the transaction's earliest `AttributionTouches` row wins. Presenting a different code returns 400 "referral code is already bound to this sign-in". A code from an anonymous link touch is only used when the user presented none. See [Auth v3 transactions](/engineering/identity/auth-v3-transactions).

### Anonymous link touches

Landing pages on `joinyelo.com` (invite, QR, tip, and claim pages) call `POST /authv3/attribution/touch` the moment they load, before any sign-in exists. The body is the same attribution object Auth v3 accepts with legal acceptance:

```json
{
  "anonymous_id": "4f9c2a7e-1b3d-4c8e-9a6f-2d5e7b1c0a93",
  "landing_surface": "/i",
  "referral_code": "SL-7QK2M",
  "dub_click_id": "abc123XYZ",
  "utm_medium": "qr"
}
```

The API validates the snapshot, stores it as an `AttributionTouches` row with no `auth_transaction_id`, and returns `{ "success": true }`. The endpoint uses rate scope `attribution_touch` (120 requests per 10 minutes) and is excluded from the Auth v3 funnel step metric.

When an Auth v3 transaction resolves to a user, `AssociateAuthV3TransactionAttribution` claims the transaction's own touches plus any unclaimed anonymous touches that share one of the transaction's `anonymous_id` values and were recorded within 90 days of `authenticated_at`. Claimed touches join the user's first-touch and last-touch attribution. A click made before the app was installed still reaches the account, as long as the sign-up runs in the same browser cookie jar.

### Dub lead tracking

`fireDubTrackLead` sends `Track.Lead` with event name `Sign Up`, the Dub click ID, and the user ID as the customer external ID. It runs on a detached 10-second context and is skipped when `dubID` is empty. The Auth v2 community path calls it.

Auth v3 reports signups the same way. After `FinishProfile` completes, the API reads the most recent `dub_click_id` from the user's claimed touches (`GetAuthV3UserDubClickID`). If one exists, `authV3DubLeadTracker` sends a `Sign Up` lead on a detached 10-second context. A failure only logs "[authv3] Dub TrackLead failed".

### Acquisition source

`SetAcquisitionSourceIfDefault` runs `UPDATE "Users" SET acquisition_source = $source WHERE id = $id AND acquisition_source = 'app_organic'`. A more specific source is never overwritten.

| Caller | Source written |
| --- | --- |
| `AuthV2Service.applyReferralCode` | `app_referral` |
| `service/tipping/tipping.go` (two paths) | `qr_payment` |
| `service/worldcup/world_cup.go` | `event_link` |

## Rewards

Rewards are derived by `GetUserReferrals` and `GetReferrers` in `queries/referral.sql`. Nothing is stored per referral.

- A referee counts as an active driver if they have any ride as driver with `status = 'complete'` and `cancel_phase IS NULL`.
- Otherwise they count as an active rider if they have such a ride as rider.
- The reward row is the one for the referee's community whose window contains `referral_time` (`BETWEEN start_time AND end_time`).
- Driver activity earns `driver_value`. Rider-only activity earns `rider_value`. No completed ride earns 0.
- Outstanding is total earned minus `SUM(ReferralPayouts.amount)` for the referrer.

`UpdateReferralReward` closes the open row (`end_time = 'infinity'`) at `now()` and inserts a new row starting at the same instant, in one transaction.

**Worked example.** A community has `rider_value = 5` and `driver_value = 20`. A referrer has three referees:

| Referee | Completed rides | Value |
| --- | --- | --- |
| A | 2 as rider | 5 |
| B | 1 as rider, 4 as driver | 20 |
| C | None | 0 |

Total earned is 25. With one payout of 10, outstanding is 15.

The two queries differ:

| Aspect | `GetUserReferrals` (app) | `GetReferrers` (no route) |
| --- | --- | --- |
| Reward community | Referee's `community_id` | Referee's `home_community_id` |
| Ride filter | Any community | `Rides.community_id` equals the requested community |
| `DriverApplications` join | Inner join; referees without a row are dropped | Left join |
| Scope | One referrer | Referrers whose `community_id` matches, with at least one referee |

Driver leads have a separate referrer (`DriverLeads.referrer_user_id` or `referrer_name`), set with `PATCH /dashboard/leads/drivers/{id}/referrer` (Clerk role `admin` or `intern`). See [Driver leads](/dashboard/driver-leads).

## Invite preview and in-app connect

`GetInvitePreview` calls `GetInviterCard`, which resolves the code with `GetAuthUserByReferralCode` and then loads the user. Unknown codes return 404. The response echoes the path `code`, not the user's current code.

`UserService.ConnectFriend` resolves the same way and calls `Friendship.AddMutual` with source `referral`. It rejects unknown codes ("This invite link is invalid or has expired.") and self-invites.

On the client side, `ReferralCaptureObserver` in `yelo-frontend` calls Dub `trackOpen` 750 ms after the app becomes interactive. It stores the link key as the captured code in AsyncStorage (`@yelo/referral_code`) and the Dub click ID in `@yelo/referral_click`. `normalizeInviteCode` uppercases only codes matching the generated format.

When a universal link opens the invite screen for a signed-out user, the app calls `trackOpen` itself, because the click never reached Dub. The returned click ID is stored in `@yelo/referral_click`. The share medium (`utm_medium`, or `qr` when the link carries `qr=1`) is passed to the invite screen and stored there too. Auth v3 forwards both as `dub_click_id` and `utm_medium` on native attribution, and as `dub_id` and `utm_medium` on the hosted sign-in URL. `clearCapturedCode` removes both keys.

The QR bottom sheet appends `qr=1` to the encoded link only, so Dub counts scans separately from shared or copied links.

### Invite landing page

Personal invite links land on `joinyelo.com/i/<code>`, served by the signup site through the experience router. The page must stay on `joinyelo.com` so its cookies are first-party to `/auth/v3`. On load it:

- Plants `yelo_anon_id` and, when the URL carries `dub_id`, a `dub_id` cookie on `.joinyelo.com` (90 days, `SameSite=Lax`).
- Calls `POST /authv3/attribution/touch` with `keepalive`, so the request outlives an immediate App Store redirect.
- Redirects Apple mobile devices to the App Store with `ct=<code>`.
- Leads with the store for the device. The primary button reads **Continue → App Store**, or **Continue → Google Play** on Android. On Android it links to Google Play with `referrer=deepLink=https://join.yelo.link/<code>`, which the Dub SDK reads on first open.
- Shows a secondary **Continue → web** link that forwards the code and the allowlisted attribution parameters (`dub_id`, `utm_*`, `source_channel`, `channel`, `ref`, `referral_code`) to `/auth/v3`. Other parameters, including `qr` and `v`, are dropped.

Fleet driver invites land on `joinyelo.com/i/fleet/<code>` on the same site. `invite.yelo.link` only forwards links shared before the move: `invite.yelo.link/<code>` and `invite.yelo.link/fleet/<code>` redirect to the matching `https://joinyelo.com/i/...` path with the query string preserved, and the root `invite.yelo.link/` returns a 302 to `https://joinyelo.com/`.

## Path shortener

`LinkService.Encode` stores `NewShortenedPathRecord(path)`: an 8-character code from `math/rand` over `[a-zA-Z0-9]` (62^8 possible values). `Decode` reads it back. There is no TTL and no ownership.

The mobile app decodes these in `app/(app)/link.tsx`. It handles `com.rideyelo://link?yeloLink=<code>`, waits 1 second, then navigates to the decoded path. `SocialContext.encodeLink` builds `http://redirect.rideyelo.com/?deepLink=com.rideyelo://link?yeloLink=<code>`, but no component calls it.

## Deep-link redirect

`GET /redirect` renders the inline `redirectTemplate` in `router.go`. It sets `window.location.href` to `APP_URL_SCHEME` (default `com.rideyelo://`), then to `APP_STORE_URL` after 1,000 ms. It ignores query parameters.

`internal/server/http/redirect.html` is a different page. It reads `deepLink` and `appStore` from the query string. No Go code references it. The mobile app links to `http://redirect.rideyelo.com/?deepLink=...` (`lib/navigation/deepLink.ts`, `SocialContext.tsx`), which matches the query-string variant.

## Gotchas and edge cases

- **Lookups disagree on legacy codes.** `GetAuthUserByReferralCode` matches `old_referral_code` and is case-sensitive. `GetAuthV3ReferrerIDByCode` ignores `old_referral_code`. An old code previews fine on the invite page but fails Auth v3 sign-up with "referral code is invalid".
- **The preview echoes the path code.** `GetInvitePreview` returns `ReferralCode: code`. The mobile invite screen stores `preview.referral_code`, so a legacy code stays legacy.
- **`GetAuthUserByReferralCode` has no limit or status filter.** It is a `:one` query with no `ORDER BY`. Deleted or banned users still resolve in Auth v2, preview, and connect paths.
- **A user without a code gets one from `GET /referral/link`.** An empty code has no hyphen, so a new code is generated and `old_referral_code` is set to the empty string.
- **Missing Dub key fails the request for new links.** The `dubClient == nil` guard never fires because `service.go` always constructs a client. With `DUB_API_KEY` unset, `GET /referral/link` returns 500 for users without a link. Users with an existing link still get it back.
- **First-byte initials.** `GenerateReferralCode` takes `trimmed[0]`, a byte. A name starting with a multi-byte character such as "Élise" produces a Latin-1 rune (`Ã`), not `E`.
- **The sweep only repairs existing links.** Users with `share_link_created_at IS NULL` are never swept. Their link is created on demand.
- **Ambient referrals need a shared cookie jar.** Anonymous touches are claimed by `anonymous_id`. A landing in one browser and a sign-up in another (or in the app's native flow, which uses a per-install ID) don't link up.
- **Reward boundaries overlap.** `BETWEEN` is inclusive at both ends, and a reward switch sets the old `end_time` equal to the new `start_time`. A referral at exactly that instant matches both rows.
- **Shortener errors are 500s.** `GetByEncodedPath` wraps "no rows" as a server error, so an unknown code returns 500, not the documented 404. `Insert` doesn't retry on a primary-key collision; `ShortenedPathRecord.Regenerate` is never called. Paths longer than 255 characters fail the insert with 500.
- **The shortener is unauthenticated.** Anyone can write rows to `ShortenedLinks` through `POST /link/encode`.
- **Friendship on referral is Auth v2 only.** The Auth v3 path writes only the `Referrals` row. It doesn't add the friendship or promote `acquisition_source`.
