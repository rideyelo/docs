This page indexes every file in `yelo-api/migrations/`. Use it to find when a table or column appeared, which pull request shipped it, and which migrations rewrote or removed data. For the current shape of each table, see the [database reference](/reference/database/overview). For how migrations run in production, see [Deployment](/engineering/deployment) and [Failed migration](/runbooks/failed-migration).

## How to read this log

- **Migration** is the file name without `.up.sql`. golang-migrate applies files in numeric order and records the highest version in `schema_migrations`.
- **Date** is the commit date of the first commit that added the file under its current number. A migration renumbered to resolve a collision shows the renumbering date.
- **PR** is the GitHub pull request that merged the commit. Migrations before `000161` predate the GitHub pull request history and show a dash. Several early-2026 PRs merged into `dev` or a version branch rather than `main` (`#3`, `#7`, `#8`, `#9`, `#10`, `#11`, `#16`). Those changes reached `main` through [#12](https://github.com/rideyelo/yelo-api/pull/12) on 2026-04-04 and [#17](https://github.com/rideyelo/yelo-api/pull/17) on 2026-06-17. Summer 2026 work reached `main` through the 5.6.0 release PR [#30](https://github.com/rideyelo/yelo-api/pull/30) on 2026-08-03.
- **Flags**:
  - **Backfill** rewrites or copies existing rows (`UPDATE`, `INSERT ... SELECT`, or a trigger-driven seed).
  - **Destructive** drops a table or a populated column, or deletes rows. The down migration can't restore the data.
  - **River** marks the vendored River job queue schema. River owns these tables; don't edit them by hand.

## Quirks and incidents

- **Duplicate rename in 000083.** Migrations 082 and 083 both rename `car_size` to `vehicle_size`. `scripts/release/run-migrations.sh` migrates a fresh database to 82 and then forces 83. `internal/data/migrationprep` skips 83 for test databases and the sqlc schema.
- **Renumbering on collision.** Parallel branches sometimes claimed the same number. The later branch renames its files before merge. For example, `a2c03869` renamed `000265_auth_v3_otp_delivery` to `000266` to resolve a collision with `main`. Dates in this log reflect the final file name.
- **000267 applied before it merged.** `000267_auth_v3_web_sessions` reached production from an unmerged branch. [#74](https://github.com/rideyelo/yelo-api/pull/74) copied the exact migration pair into `main` so the release runner saw a clean version 267.
- **000270 failed in production.** A B-tree index on `Locations.mapbox_id` hit a 3,584-byte legacy value, above the 2,704-byte B-tree entry limit, and left `schema_migrations` dirty at 270. [#93](https://github.com/rideyelo/yelo-api/pull/93) added 271 to replace it with a hash index and made release failures visible.
- **000280 failed in production.** A legacy user with a zero-UUID `school_id` broke the education proof backfill. The migration rolled back and the marker was repaired to 279. [#119](https://github.com/rideyelo/yelo-api/pull/119) filtered the backfill to existing schools.
- **Concurrent indexes.** 165, 189, 270, and 288 to 291 use `CREATE INDEX CONCURRENTLY`. Keep one concurrent statement per file, because golang-migrate submits a whole file as one execution.
- **Schema drift repair in 000347.** Production already had a unique constraint on `Locations.address` that no migration created. 347 adds it only where it's missing.
- **River tables are vendored.** 242 to 248 reproduce River's schema migrations v1 to v7 as golang-migrate files. No code runs River's own migrator (`rivermigrate`), so a River upgrade that changes its schema needs a new numbered migration.
