---
title: "Feature flags and runtime gates"
description: "Every switch that changes Yelo behavior at runtime: API environment toggles, the X-Features header, app-version gates, experiments, admin-editable settings, per-entity flag columns, and client build toggles."
---

Yelo has no feature flag service. Behavior is switched by seven kinds of gates:

1. API environment variables, read once at startup.
2. Request headers that a client sends per request.
3. A single store-version floor.
4. Experiment keys stored on users and communities.
5. Admin-editable settings rows in Postgres.
6. Boolean and enum columns on communities, users, fleets, and other rows.
7. Build-time variables in the web and mobile clients.

<Note>
Neither client reads PostHog feature flags, and the API never evaluates them. PostHog is used for events, session replay, and metrics only.
</Note>

**Path conventions.** API paths are relative to `yelo-api/internal/`, with these abbreviations:

- `config.go` is `utilities/config/config.go`.
- `main.go` is `yelo-api/cmd/api/main.go`.
- `queries/` is `data/repository/queries/`.

Mobile paths are relative to `yelo-frontend/`, and web paths to `yelo-web/`.

**Who can change it** uses these values:

- **Deploy**: an environment variable on Cloud Run or the build.
- **Admin**: the Clerk dashboard `admin` role. See [Dashboard roles](/administration/dashboard-roles).
- **Self**: the signed-in app user.
- **Client**: the app or site that sends the request.
- **SQL**: no API writer exists, so it needs a migration or a manual query.

## Server fields the app ignores

The API returns these, but the mobile app never branches on them:

- User: `is_banned`, `is_deleted`, `is_power_driver`, `is_terms_agreed`, `is_verified`, `is_waitlisted`, `has_dub_link`.
- Community: `is_asleep`, `is_hidden`, `limited_hours_enabled`, `low_supply`, `extensions`.
- Fleet: `has_custom_payouts`, `is_student_only`.
- Ride request: `tips_enabled` in the body, because the server overwrites it from `X-Features`.
