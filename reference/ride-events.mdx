The ride event log is an append-only audit trail of what happened to a ride. The API writes rows to the `"RideEvents"` table, and admins read them in the dashboard ride timeline. This page lists every event type, where it is recorded, and what each row contains.

For the statuses and transitions themselves, see [Ride lifecycle](/concepts/ride-lifecycle). For cancellation rules and fees, see [Cancellations](/concepts/cancellations). For how the ride service is structured, see [Rides implementation](/engineering/api/rides-implementation). For the dashboard UI, see [Rides](/dashboard/rides#open-ride-details).

<Note>
All file paths on this page are relative to the `yelo-api` repository unless they start with `yelo-web/`.
</Note>

<Warning>
Ride events are diagnostics, not a source of truth. Rows written through the recorder are asynchronous and can be dropped. Rows written by a ride operation commit with the change they describe, but they carry a sanitized subset of it. Never use the log to drive lifecycle decisions. Read the `"Rides"` row for current state.
</Warning>

## Table schema

Migration `migrations/000186_ride_events.up.sql` creates the table. No later migration alters it. The table name is `"RideEvents"`, quoted and in PascalCase like the other tables. It is not `ride_events`.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `BIGINT GENERATED ALWAYS AS IDENTITY` | Primary key. Breaks ties when two events share a `created_at`. |
| `ride_id` | `UUID NOT NULL` | Foreign key to `"Rides"(id)`, with no `ON DELETE` action. |
| `event_type` | `TEXT NOT NULL` | One of the values below. There is no enum or `CHECK` constraint. |
| `actor_id` | `UUID` | The user who caused the event. Null for most system events. |
| `actor_type` | `TEXT` | `rider`, `driver`, or `system` (`internal/models/ride_event.go:47`). Not constrained. |
| `old_status` | `TEXT` | Ride status before the transition, if the event records one. |
| `new_status` | `TEXT` | Ride status after the transition, if the event records one. |
| `metadata` | `JSONB` | Event-specific payload. See each event below. |
| `created_at` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | Set by Postgres at insert time, not when the event happened. |

| Index | Columns | Used for |
| --- | --- | --- |
| `idx_ride_events_ride_id` | `(ride_id, created_at)` | One ride's timeline |
| `idx_ride_events_type` | `(event_type, created_at)` | Fleet-wide queries by event type |

The Go model is `models.RideEvent` in `internal/models/ride_event.go:55`. `models.RideEventWithActor` (`internal/models/ride_event.go:67`) adds `actor_name`.

Ride statuses in `old_status` and `new_status` use the values from `internal/models/ride.go:41`. A finished or canceled ride is stored as `complete`, not `completed`.

## How events are written

### The async recorder

Almost every event goes through `rideevents.EventRecorder` in `internal/service/rideevents/recorder.go`:

1. The caller runs `Record(ctx, RecordOpts)`, which builds a `models.RideEvent` and pushes it onto a buffered channel. The buffer holds 500 events (`recorder.go:15`).
2. If the channel stays full for 100 ms (`recorder.go:16`), the event is dropped. The recorder logs `Ride event dropped: channel full after timeout`.
3. One goroutine started by `Start` (`cmd/api/main.go:246`) reads the channel and calls `InsertRideEvent` for each event. It uses the sqlc query `InsertRideEvent` in `internal/data/repository/queries/engagement.sql:530`.
4. Insert failures log `Failed to insert ride event` and are never retried or returned to the caller (`recorder.go:100`).

The recorder instance is built once in `internal/service/service.go:109`. The ride service, the activation service (`internal/service/service.go:184`), and the notification queue workers (`cmd/api/main.go:328`) all share it.

### Writes are not transactional

Recorder writes are not part of the ride's transaction:

- The recorder inserts on its own connection, after the `Record` call returns. A successful ride change can end up with no event if the buffer is full, the insert fails, or the process stops.
- Some events are recorded before the state change they describe, so they can exist even when the change fails. Example: `activation_tier_reached` is recorded before the notification is enqueued.
- `created_at` is the insert time. Under load it can lag the real event, and `elapsed_since_previous_ms` inherits that lag.

Two kinds of event are transactional. Ride operation events are covered in [Ride operation events](#ride-operation-events). The other is `message_sent`. The `InsertMessageTimeline` query (`internal/data/repository/queries/messaging.sql:49`) runs inside the same transaction as the message insert in `AppendMessage` (`internal/data/repository/messaging.go:55`). It is written as raw SQL with the literal string `'message_sent'` and does not use the recorder.

### Ride operation events

Acceptance, promotion, completion, cancellation, requeue, expiry, and tips run as ride operations. Their events don't use the recorder.

- `recordOperationEventTx` in `internal/data/repository/ride_operation_events.go:16` runs inside `FinishTx` when an operation moves to `succeeded` (`ride_operation.go:222`). It calls `InsertRideEvent` on the transaction that commits the ride change and the operation outcome. The event exists if and only if the change committed.
- An operation that ends `failed` or `quarantined` writes no event. A declined card authorization, for example, cancels the ride without a `ride_canceled` row.
- A replayed finalizer returns before the insert, so each operation writes its event once.
- Every row carries `operation_id`, the ID of the `RideOperations` row. Join on it to see the command's frozen inputs and step receipts.
- `actor_id` and `actor_type` are the operation's. A system operation has `actor_type = 'system'` and a null `actor_id`.
- `new_status` is the ride's status read under lock in the same transaction. `old_status` is fixed per kind, or the status frozen in the operation's inputs.
- Metadata is a projection of the frozen inputs: `reason`, `queued`, `requeue`, `automatic`, and dollar amounts converted from `fare_cents`, `tip_cents`, and `fee_cents`. PaymentIntent IDs, connected accounts, and mandate data stay in the journal.

`ride_auto_queued` is the one operation event written at reservation instead of at the outcome (`ride_acceptance_operation.go:231`). It commits with the assignment.

See [Timeline events](/engineering/payments/ride-operation-journal#timeline-events).

### Shutdown

`main.go` calls `EventRecorder.Stop()` (`cmd/api/main.go:531`), which closes the channel and returns right away. It does not wait for the insert goroutine to drain. The goroutine also inserts with the root `ctx` passed to `Start`, and that context is already canceled at shutdown. Buffered events are likely lost on every deploy.

## Event types

`internal/models/ride_event.go:11` defines 33 event types. The tables below list each call site that records them. **Status** shows `old_status → new_status`. A dash means the column is null.

Common metadata keys:

- `pickup_name`, `dest_name`, and `destination_name` are the display names of the pickup and destination.
- `distance` is the ride's route distance.
- `elapsed_since_*_ms` values are measured with `time.Since` when the event is recorded.

### Defined but never written

- `merchant_selected`, `payment_intent_created`, `payment_processing_failed`, `payment_confirmed`, `payment_canceled`, `pickup_route_calculated`, and `ride_board_removed` were written by the ride service before ride money moved to ride operations. `payment_intent_created` has no recorder left. The helpers for the others remain in `internal/service/ride/events.go` and have no caller. Rides from before the cutover still have these rows, and the dashboard summary switch still lists the types.
- `direct_assigned` (`RideEventDirectAssigned`) has a helper, `recordDirectAssignedEvent` (`internal/service/ride/events.go:386`), that is only called from `events_test.go`. Direct requests now leave the ride unmatched until the driver accepts (`internal/service/ride/rider.go:449`), so a direct match shows up as `notification_dispatched` with `direct_request: true`, followed by `ride_accepted`. The dashboard summary still treats `direct_assigned` as a match (`internal/service/dashboard/rides.go:107`).

### Written as a raw string

- `message_sent` is inserted by SQL with the literal `'message_sent'` (`internal/data/repository/queries/messaging.sql:51`). The `RideEventMessageSent` constant is only referenced by the dashboard summary switch.

All other event types are written through `models.RideEvent*` constants.

## Reading events

### Dashboard endpoint

`GET /dashboard/rides/{id}/events` returns one ride's timeline. It is registered in `internal/server/http/dashboard/rides/rides_routes.go:26` under the `/dashboard/rides` group (`internal/server/http/router.go:552`), with operation ID `dashboard.GetRideEvents`.

- **Auth:** A Clerk dashboard session with role `admin` (`rides_handler.go:132`). Other roles get `403 admin access required`.
- **Errors:** A path ID that isn't a UUID returns `400 invalid ride ID`. An unknown ride returns `200` with an empty `events` array.
- **Query:** `ListRideEventsByRideID` (`internal/data/repository/queries/engagement.sql:544`) left-joins `"Users"` on `actor_id` to build `actor_name` and orders by `created_at ASC, id ASC`.

The response is wrapped in the standard envelope, with `success`, `data`, and `metadata` fields:

```json
{
  "success": true,
  "data": {
    "events": [
      {
        "id": 1234,
        "ride_id": "2f6c…",
        "event_type": "ride_accepted",
        "actor_id": "9a1e…",
        "actor_type": "driver",
        "actor_name": "Jordan Lee",
        "old_status": "confirmed",
        "new_status": "driver_en_route",
        "metadata": { "operation_id": "5b0d…", "queued": false, "automatic": false },
        "created_at": "2026-09-20T02:14:07.512Z",
        "elapsed_since_previous_ms": 41250
      }
    ],
    "summary": {
      "time_to_match_ms": 41250,
      "time_to_pickup_ms": 312000,
      "ride_duration_ms": 604000,
      "total_events": 18,
      "total_declines": 1
    }
  }
}
```

`GetRideEvents` in `internal/service/dashboard/rides.go:70` computes the derived fields:

| Field | How it's computed |
| --- | --- |
| `elapsed_since_previous_ms` | `created_at` minus the previous row's `created_at`. Null on the first row. |
| `time_to_match_ms` | The last `ride_accepted`, `ride_auto_queued`, or `direct_assigned` time minus the last `ride_confirmed` time. `queue_promoted` does not count. |
| `time_to_pickup_ms` | The first `driver_at_pickup` in the list minus the last match time |
| `ride_duration_ms` | `ride_completed` time minus the last `rider_picked_up` time |
| `total_events` | Row count |
| `total_declines` | Count of `ride_declined` rows |

### Dashboard UI

In `yelo-web`, `useRideEvents` (`src/hooks/useRideEvents.ts`) calls the generated `dashboardGetRideEvents`. `RideEventsTimeline` (`src/sites/dashboard/components/RideEventsTimeline.tsx`) renders the timeline inside `RideDetailSheet` (`src/components/rides/RideDetailSheet.tsx`). The sheet opens from the Rides trips table, the Issues tab, the live operations tables (`src/components/live/LiveTables.tsx`), and recent pricing activity.

- Badge colors cover 19 event types (`RideEventsTimeline.tsx:11`). Other types use the default zinc badge.
- `notification_dispatched` rows get a bell icon. They are meant to expand into notification details through `dashboardGetNotificationDetail`, which reads `metadata.notification_log_id` (`RideEventsTimeline.tsx:138`). The orchestrator writes `notification_id` instead, so the row falls back to showing raw metadata JSON. The row label reads `metadata.title`, which no writer sets, so it shows the actor name or a dash.

### Other consumers

There is no rider or driver API for ride events. The mobile app (`yelo-frontend`) does not read them. The only other code that touches the table is the E2E fixture cleanup, which runs `DELETE FROM "RideEvents"` before deleting fixture rides (`internal/server/http/e2econtrol/ride_fixture.go:70`).

## Query a ride's history in SQL

Run these read-only queries against the API database. Replace the UUIDs with real values.

Get the full timeline for a ride, in the dashboard's order, with actor names:

```sql
SELECT e.id,
       e.created_at,
       e.event_type,
       e.actor_type,
       COALESCE(u.first_name || ' ' || u.last_name, '') AS actor_name,
       e.old_status,
       e.new_status,
       e.created_at - LAG(e.created_at) OVER (ORDER BY e.created_at, e.id) AS since_previous,
       e.metadata
FROM "RideEvents" AS e
LEFT JOIN "Users" AS u ON u.id = e.actor_id
WHERE e.ride_id = '00000000-0000-0000-0000-000000000000'
ORDER BY e.created_at, e.id;
```

Show only status transitions:

```sql
SELECT created_at, event_type, old_status, new_status, actor_type
FROM "RideEvents"
WHERE ride_id = '00000000-0000-0000-0000-000000000000'
  AND new_status IS NOT NULL
ORDER BY created_at, id;
```

List decline reasons for a ride:

```sql
SELECT created_at,
       metadata->>'driver_id'                AS driver_id,
       metadata->>'reason'                   AS reason,
       (metadata->>'elapsed_since_confirm_ms')::bigint AS ms_since_confirm
FROM "RideEvents"
WHERE ride_id = '00000000-0000-0000-0000-000000000000'
  AND event_type = 'ride_declined'
ORDER BY created_at;
```

Trace activation and notifications for an unmatched ride:

```sql
SELECT created_at,
       event_type,
       metadata->>'tier'             AS tier,
       metadata->>'drivers_notified' AS drivers_notified,
       metadata->>'template_code'    AS template_code,
       metadata->>'recipient_count'  AS recipient_count,
       metadata->>'status'           AS dispatch_status
FROM "RideEvents"
WHERE ride_id = '00000000-0000-0000-0000-000000000000'
  AND event_type IN ('notification_dispatched', 'activation_tier_reached',
                     'rescue_alert_sent', 'no_drivers_available')
ORDER BY created_at, id;
```

Count event types over the last 7 days. This query uses `idx_ride_events_type`:

```sql
SELECT event_type, COUNT(*) AS events
FROM "RideEvents"
WHERE created_at >= now() - interval '7 days'
GROUP BY event_type
ORDER BY events DESC;
```

Find payment failures by operation in one community:

```sql
SELECT e.created_at,
       e.ride_id,
       e.metadata->>'operation' AS operation,
       e.metadata->>'error'     AS error
FROM "RideEvents" AS e
JOIN "Rides" AS r ON r.id = e.ride_id
WHERE e.event_type = 'payment_processing_failed'
  AND r.community_id = '00000000-0000-0000-0000-000000000000'
ORDER BY e.created_at DESC
LIMIT 100;
```

Find confirmed rides that have no `ride_confirmed` event, which points to dropped events:

```sql
SELECT r.id, r.status, r.confirm_time
FROM "Rides" AS r
WHERE r.confirm_time >= now() - interval '1 day'
  AND NOT EXISTS (
    SELECT 1 FROM "RideEvents" AS e
    WHERE e.ride_id = r.id AND e.event_type = 'ride_confirmed'
  )
ORDER BY r.confirm_time DESC;
```

<Tip>
`metadata` is `JSONB`, so use `->>` for text and cast numbers explicitly. Key names vary by event. For example, `ride_requested` uses `destination_name`, while most trip events use `dest_name`. Check the tables above before filtering.
</Tip>

## Add a new event type

1. Add a `RideEvent*` constant in `internal/models/ride_event.go`. No migration is needed because `event_type` is unconstrained `TEXT`.
2. Add a `record*Event` helper in `internal/service/ride/events.go`. Record after the state change commits and set `OldStatus` and `NewStatus` when the event is a transition.
3. Add the constant to the `applyEventToTimings` switch in `internal/service/dashboard/rides.go:104`. The switch is exhaustive, and the linter flags missing cases.
4. Optionally, add a badge color in `yelo-web/src/sites/dashboard/components/RideEventsTimeline.tsx`.
