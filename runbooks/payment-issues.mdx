---
title: "Payment failures and holds"
description: "Diagnose failed ride authorizations, holds that weren't released, captures that didn't happen, and cancellation fee disputes"
---

Yelo authorizes a ride when a driver accepts it, and captures later with an explicit amount. Every PaymentIntent lives on the driver's or fleet's Stripe connected account, saved as `Rides.stripe_merchant_id`. Each of those Stripe calls is a step of a ride operation, recorded in `RideOperations` and `RideOperationSteps` before it runs. Read [Payments and payouts](/concepts/payments-and-payouts) and [Cancellations](/concepts/cancellations#how-fees-are-charged) first.

## Symptoms

- A driver's accept fails with **Payment Failed**, and the ride is canceled.
- A driver's accept, complete, or cancel returns an error, and afterwards every action on the ride returns **Ride Unavailable**.
- A rider reports a pending charge for a ride that expired or was canceled with no fee.
- A driver reports a completed ride with no payout, or a tip that never arrived.
- A rider disputes a cancellation fee.
- Logs contain `ride operation delivery recovery` at warn level, or `needs manual review`.

## Diagnose

<Steps>
  <Step title="Read the ride's payment fields">
    **Read-only.** Never select `Rides.payment_intent_client_secret`.

    ```sql
    BEGIN TRANSACTION READ ONLY;

    SELECT id, status, price, discounted_price, tips_enabled, tip_amount, driver_payout,
           payment_intent_id, tip_payment_intent_id, pre_auth_amount, stripe_merchant_id,
           cancel_phase, cancel_user, cancel_reason, complete_time, tip_window_expires_at
    FROM "Rides" WHERE id = '<ride-id>';

    SELECT created_at, event_type, actor_type, old_status, new_status, metadata
    FROM "RideEvents"
    WHERE ride_id = '<ride-id>'
      AND event_type IN ('ride_accepted', 'queue_promoted', 'ride_completed', 'ride_canceled',
                         'auto_requeued', 'no_drivers_available',
                         'tip_captured', 'tip_window_expired')
    ORDER BY created_at;

    ROLLBACK;
    ```

    `driver_payout` is written by the ride operation that settles the ride: the fare at completion, fare plus tip at rating, or the fee at cancellation. The `payment_intent.succeeded` webhook skips any ride that has a ride operation.

    Read the PaymentIntent's live status in Stripe, on the connected account in `stripe_merchant_id`. The legacy `PaymentIntents` table has no current writer, so it has no rows for current rides. See [PaymentIntents](/reference/database/payments#paymentintents).
  </Step>
  <Step title="Read the ride's operations">
    **Read-only.** This shows every financial command on the ride, whether it finished, and which Stripe step is open.

    ```sql
    BEGIN TRANSACTION READ ONLY;

    SELECT id, kind, state, actor_type, outcome, created_at, finished_at
    FROM "RideOperations" WHERE ride_id = '<ride-id>' ORDER BY created_at;

    -- request holds the exact PaymentIntent, account, and amount. Never paste it into a ticket in full
    SELECT s.operation_id, s.name, s.first_attempt_at, s.resolved_at,
           COALESCE(s.request->>'payment_intent_id', s.request->>'intent_id',
                    s.result->>'payment_intent_id') AS payment_intent_id,
           COALESCE(s.request->>'amount', s.request#>>'{request,amount}') AS amount_cents,
           s.result IS NULL AS unresolved
    FROM "RideOperationSteps" s
    JOIN "RideOperations" o ON o.id = s.operation_id
    WHERE o.ride_id = '<ride-id>'
    ORDER BY s.first_attempt_at;

    ROLLBACK;
    ```

    | State | Meaning |
    | --- | --- |
    | `succeeded` | The Stripe steps and the ride change committed together |
    | `failed` | Stripe confirmed nothing was charged: a declined authorization or a canceled tip |
    | `pending` | Still being worked. A `ride_operation` River job retries it. The ride accepts no other command meanwhile |
    | `quarantined` | Stripe's state is unknown or contradicts the recorded decision, or the job ran out of attempts. Nothing retries. `outcome.reason` names the step |

    A PaymentIntent that isn't on the ride row yet is in the `create_authorization` or `create_tip` step's `result`. See [Ride operation journal](/engineering/payments/ride-operation-journal).
  </Step>
  <Step title="Search the logs">
    Search Cloud Logging for the ride ID and these messages:

    | Message | Meaning |
    | --- | --- |
    | `ride operation delivery recovery` (warn, `quarantined` above 0) | A `pending` operation's job was discarded or cancelled, and the operation was quarantined. |
    | `ride operation delivery recovery` (info, `requeued` above 0) | A lost `ride_operation` job was restored. |
    | `Assigned ride awaits durable preparation` | An auto-queue assignment committed, but its authorization or route didn't finish in the request. The job retries it. |
    | `ride stuck past tip window for >1 hour, needs manual review` | The tip-window sweeper keeps failing on this ride. |
    | `failed to auto-capture expired tip window, will retry next run` | One sweeper attempt failed. It retries every 5 minutes. |

    A rematch after a driver cancels never reuses a hold. The requeue voids the previous driver's authorization before the ride goes back on the board, and the next accept creates a new one.

    An open `stripe` circuit breaker posts to Slack and makes wrapped Stripe calls, such as SetupIntents and account lookups, fail fast. Ride authorizations, captures, voids, and tips aren't wrapped by the breaker. See [Integrations](/engineering/api/integrations#resilience).
  </Step>
  <Step title="Find expired rides that kept a hold">
    Expiry voids any remaining hold before it completes the ride, so this query should return nothing for rides that expired after the ride command runtime shipped. Rows from before that can still hold an authorization. **Read-only:**

    ```sql
    SELECT id, stripe_merchant_id, payment_intent_id, pre_auth_amount, complete_time
    FROM "Rides"
    WHERE status = 'complete' AND cancel_reason = 'automatic'
      AND payment_intent_id IS NOT NULL
      AND complete_time > now() - interval '7 days'
    ORDER BY complete_time DESC;
    ```
  </Step>
</Steps>

### Cases and what the code does

| Case | What happens in code | Operator action |
| --- | --- | --- |
| Accept fails with **Payment Failed** | The card authorization ended canceled. The `accept` operation is `failed`, the ride is `complete` with `cancel_reason = 'Payment Failed'`, and the rider got `ride_payment_failed` | None required. The rider needs a different card on their next request. |
| Accept fails with a server error and the ride is assigned | A Stripe or routing call failed after the assignment committed. The `accept` operation is `pending` and its job retries | Wait for the retry. If it becomes `quarantined`, escalate. |
| Canceled with no fee | The `cancel` operation's `void` step canceled the PaymentIntent, releasing the full hold | Confirm `ride_canceled` in the timeline with `fee` of 0, and a resolved `void` step. |
| Admin silent cancellation | Only allowed when the effective fare is 0 and `payment_intent_id` and `tip_payment_intent_id` are null. No Stripe call is made | Nothing to reconcile. The `ride_canceled` event records `cancellation_fee` 0 and `cancel_reason` is `admin_silent_cancellation`. A paid ride is refused with "This ride requires payment review before it can be canceled." |
| Canceled with a fee | The `capture` step captured the quoted fee with `amount_to_capture`, and Stripe released the rest | Check `fee` on the `ride_canceled` event against [Fee rules](/concepts/cancellations#fee-rules). The quote is in `RideCancellationQuotes`. |
| Expired after a requeue | The requeue already voided the hold. Expiry voids any hold that is still attached | Nothing to release. |
| Tip window never closed | `TipCapture` submits a system `settle_tip` operation after `tip_window_expires_at`, retrying every 5 minutes | Wait. Escalate if the "stuck past tip window" log appears, and read the ride's `settle_tip` operation. |
| Capture succeeded but the ride didn't change | The `capture` step has a result and the operation is still `pending` | Wait. The job finalizes from the stored receipt without calling Stripe again. |
| Operation `quarantined` | Nothing retries, and the ride accepts no other command | No Yelo tool resolves it. Escalate to an engineer with the operation ID. See the warning below. |

<Warning>
Yelo has no endpoint, dashboard control, or script that refunds, captures, or cancels a PaymentIntent, or that resolves a quarantined ride operation, and the API never creates refunds. Admin silent cancellation doesn't change this: it refuses any ride with a fare or a PaymentIntent. `scripts/create_payment_link` only creates a payment link on one hard-coded account. Any refund or manual release happens outside Yelo tooling, on the connected account in `Rides.stripe_merchant_id`. Record the ride ID and PaymentIntent ID in the ticket.
</Warning>

## Fix

<AccordionGroup>
  <Accordion title="Option 1: Let the automatic paths finish">
    - **Tip-enabled ride waiting on the rider.** The rider rates, which captures fare plus tip. Otherwise `TipCapture` captures the fare after 24 hours.
    - **Declined card at accept.** Nothing to repair. The ride was canceled and the rider was told.
    - **Operation `pending`.** The `ride_operation` job retries the open step with the same idempotency key. If the job itself is lost, `ride_operation_recovery` restores it within a minute.
    - **Missing `driver_payout`.** Read the ride's operations. `driver_payout` is written when the `complete`, `settle_tip`, `tip`, or `cancel` operation finishes, so a null value means that operation hasn't finished.
  </Accordion>
  <Accordion title="Option 2: Fee dispute">
    Compare `cancel_phase`, `cancel_user`, and the ride timestamps with [Fee rules](/concepts/cancellations#fee-rules). The `ride_canceled` event records `reason`, `fee`, and the `operation_id`. The operation's `inputs` hold the frozen status and fee, and `RideCancellationQuotes` holds the quote the rider accepted. If the fee was charged by the rules and still needs reversing, that's a refund outside Yelo. See the warning above.
  </Accordion>
  <Accordion title="Option 3: Stripe outage">
    While Stripe is unreachable, accepts, completes, cancels, and tips return errors and leave their ride operations `pending`. Each operation's job keeps retrying, and the tip-window sweeper retries every 5 minutes. After Stripe recovers, list operations that are still unresolved and check that the count falls:

    ```sql
    SELECT kind, state, count(*), min(created_at) AS oldest
    FROM "RideOperations"
    WHERE state IN ('pending', 'quarantined')
    GROUP BY kind, state ORDER BY oldest;
    ```

    An operation whose job exhausted its attempts during the outage is `quarantined` with `outcome.reason = 'job_exhausted'` and needs an engineer.
  </Accordion>
</AccordionGroup>

## Verify

- The timeline shows `ride_canceled` for a cancellation, or `ride_completed`, `tip_captured`, or `tip_window_expired` for a capture.
- The ride has no `RideOperations` row in `pending` or `quarantined`.
- `Rides.driver_payout` is set for completed paid rides.
- The PaymentIntent's status in Stripe, on the connected account, matches what you expect.

## Root causes seen in code

- **A quarantined operation has no tooling.** A provider conflict, such as a hold that expired or was changed in the Stripe Dashboard, quarantines the operation. Nothing in the API resolves it, and it blocks the ride until someone does.
- **Exhausted jobs quarantine.** A long Stripe outage can run a `pending` operation's job out of attempts. Recovery then quarantines it instead of resetting the retry budget.
- **Manual Stripe changes cause conflicts.** Canceling or capturing a ride's PaymentIntent in the Stripe Dashboard makes the next step see a state that contradicts its frozen request.
- **Queued rides are authorized late.** A ride accepted into a driver's queue gets its hold at promotion. A decline then cancels a ride the rider has been waiting on.
- **Free rides can't be tipped before they're rated.** A rating that includes a tip on a free ride fails. See [Free rides](/engineering/payments/ride-tips#free-rides).
